Playwright's recovery issue [#1588](https://github.com/microsoft/playwright-mcp/issues/1588) has a merged upstream fix in [PR #40652](https://github.com/microsoft/playwright/pull/40652). The runnable raw-run schema and grader are in [`lifecycle-scorecard-template.json`](lifecycle-scorecard-template.json) and [`grade_lifecycle_scorecard.py`](grade_lifecycle_scorecard.py); completion requires 30 trials in each of nine target-pressure scenarios, 30 per readiness-check/state pair, and 30 CDP-recovery trials for every pinned product/version. Pin versions before and after fixes where practical; measure attach and first-verified-read p50/p95 with 0/10/50 live, discarded, and crashed targets; simulate CDP loss and record recovery steps; and grade launch/reachability failure, attached-but-unresponsive pages, and failed application probes as separate outcomes. Separate configuration, reachability, responsiveness, and application health; issue reports are scenario sources, not prevalence estimates.

**Saved-flow paired probe (10 November 2026):** ten independent pairs on
agent-browser v0.42.0 and Scout used the same local mutation endpoint.
Agent-browser's saved-flow HTTP tier returned `outcome_unknown` after one
request and one effect; Scout's browser click was interrupted at the same
commit boundary, then a fresh-process same-ID retry was blocked and the shared
ledger reconciled `verified_complete`. Both arms passed 10/10 (100%; Wilson
95% interval 72.2–100%). See the [runner](run_agent_browser_saved_flow_recovery.py)
and [captured summary](reports/agent-browser-saved-flow-recovery-2026-11-10.json).
This estimates only this local protocol. It does not establish customer
reliability, integration cost, or latency.

This matrix turns the product vision into a test queue. “Ready” means the
local Scout fixture and an adapter can measure the same externally visible
predicate today; it does not mean that every product has native support for
the operation. Keep native capability and adapter composition explicit.

**Competitive readout (6 November 2026):** the current-release rerun gives Scout
a defensible but narrow lifecycle wedge: at a deliberately short 1 s HTTP idle
timeout, Scout protected a 1.8 s in-flight wait in 10/10 runs, while Playwright
MCP 0.0.84 closed its target in 10/10 matched runs. Make that behavior easy to
discover and operationally useful: expose in-flight/idle state in diagnostics,
document safe timeout defaults, and show cleanup/recovery status. Then validate
whether Go platform and QA teams value this enough to adopt Scout, using the
paired workflow study below. Do not position this result as general browser
reliability or superiority; the local probe omits resource reclamation and
post-call cleanup. The adjacent strategic opportunity remains portable,
host-verifiable recovery from uncertain mutations, where current peer catalogs
do not expose a comparable native task receipt.

**Upstream status recheck (6 November 2026):** GitHub still lists Browser Use #6298 as open and #6305 as a draft. #6298 proposes default same-tab reuse for its recovery agent, while #6305 proposes opt-in active-tab selection at initial CDP attach, with ambiguity failure and no later silent retargeting; neither is shipped. ## Recovery contract portability: next proof gate

The Go API, JSONL CLI, and MCP receipt-export path converge on
`Session.ExportTaskRunRecoveryReceiptContext`, which delegates to the shared
`ExportTaskRunRecoveryReceipt` constructor. The 12 November Chrome-backed
[live capture](reports/scout-three-surface-live-receipt-parity-2026-11-12/README.md)
extends the seeded export/schema check: ten interrupted tasks per interface
were killed after one fixture-ledger effect; all thirty same-ID retries were
blocked and host reconciliation retained exactly one effect. Each actual
interrupted receipt passed the strict Go decoder and independent Python
verifier. Thirty live interrupted/completed receipt comparisons passed
normalized field parity, with frame IDs required on every receipt; one further
operation-2 triplet passed the non-first-step gate. The fixture report records
that its ledger is the authority and that producer authentication and
independent browser binding are not established. This closes the local runtime
cross-interface gate, not the production trust or customer-value gates.

Next, connect the flow to a production-shaped transactional ledger and
authenticated owner/broker, then repeat the same predicates while independently
verifying producer, browser generation, target/frame and policy bindings. Keep
MCP owner/session namespaces isolated. In parallel, run the paired buyer task
study; local fixture success does not establish adoption value.

## Execution order

1. Extend the delayed mutation fixture and adapters first. It tests the core
   product claim and directly exercises the most costly failure mode.
2. Reuse the same runner/report format for target identity and policy-path
   tests. Do not create a single blended “reliability score.”
3. Recheck WebMCP parity on current releases, then compare whether Scout can
   carry its verification and recovery contract across UI and page-native tools
   before deciding whether a bridge merits first-class support.
4. Run the buyer study before investing in more provider integrations or a
   shared multi-tenant browser service.
5. Publish raw per-run artifacts, pinned versions, exact predicates, and
   adapter source for every comparison. Unsupported and unverified outcomes
   stay visible.

The current competitive story is a hypothesis. A feature in Scout's source,
an open issue in a competitor, or a local Scout-only pass does not prove Scout
is better. The evidence gate is repeated, matched behavior plus a user value
signal.
