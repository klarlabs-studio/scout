## Matched MCP process memory probe

On 6 November 2026, Scout and Playwright MCP 0.0.84 each ran five successful
delayed-element waits against the same 1.8 s fixture, `Ready` predicate, and
HeadlessChrome 157 browser with a 5 s idle timeout. RSS was sampled every 50
ms. Scout's standalone `scout mcp serve` process measured 20,112–21,200 KiB
(median 21,088 KiB). The Playwright MCP Node process measured 130,352–151,152
KiB (median 146,480 KiB); its isolated Chrome session measured 680,416–701,872
KiB (median 700,288 KiB). See the [summary](results/matched-mcp-memory-5x-2026-11-06.json),
the five raw Scout reports (`results/scout-mcp-memory-5x-run-*.json`), and the
five raw Playwright reports (`results/playwright-mcp-memory-5x-run-*.json`).

This is a process-category signal, not a total resource comparison: Scout used
stdio MCP while Playwright used Streamable HTTP, and the category scopes do not
include all launchers consistently. RSS summation can double-count shared
pages, and 50 ms sampling misses shorter peaks. The measurement is useful for
prioritizing a matched transport benchmark, but it is not evidence of a general
memory advantage. Reproduction commands and probe sources are in the
[benchmark README](README.md#matched-mcp-memory-probe).

## MCP profile catalog baseline

`go run ./examples/benchmark/profiles` builds Scout once, queries each profile over MCP stdio, follows every `tools/list` cursor, records all serialized tool entries, checks that `configure` is callable in `all` but unavailable in `core` and `read`, and validates the `help` tool in every profile. The 6 November 2026 v2 capture is in [`results/scout-mcp-profile-catalog-core.json`](results/scout-mcp-profile-catalog-core.json). The full `all` catalog has 103 tools and 115,873 JSON bytes. The curated `core` profile has 48 tools and 57,523 bytes (50.4% fewer than `all`); `read` has 44 and 46,081 bytes (60.2% fewer); `interact` has 60 and 72,575 bytes (37.4% fewer); `diagnose` has 50 and 57,752 bytes (50.2% fewer); `admin` has 29 and 30,665 bytes (73.5% fewer). The recorded token estimate is bytes divided by four, rounded up; it is not a model tokenizer measurement. This demonstrates reduced catalog transfer/context surface and profile call gating, not improved agent selection or task success. The v2 capture verifies that the read-only `help` tool is callable in all six profiles, its advertised tools match each complete catalog, and every workflow step is available in that profile; workflows with no available steps are omitted. It returns only workflows supported by each profile (6–9 workflows, with 14–34 distinct recipe tools) and states selector, verification, and recovery guidance. This makes the narrower catalogs self-describing, but does not establish improved agent selection or task success. Next, compare profiles on the same representative tasks with identical models, budgets, and success predicates, recording tool-selection errors, calls to completion, task success, and actual input/output tokens.

This separation mirrors a current competitor evaluation pattern: agent-browser's official suite reports deterministic context-footprint estimates separately from model-driven tool/command selection ([evaluation methodology](https://github.com/vercel-labs/agent-browser/blob/main/evals/README.md)); its MCP server also defaults to a curated `core` profile ([profile reference](https://github.com/vercel-labs/agent-browser/blob/main/skill-data/core/references/commands.md)). Therefore, treat catalog bytes as a transport/context-surface metric only. A Scout profile advantage requires matched tasks and actual provider usage counters, with verified completion and unsafe/wrong-target actions as quality guardrails. A small community benchmark also reports close task success alongside differing token counts, which is a useful hypothesis but not broad comparative evidence ([web-agent-bench](https://github.com/nsosio/web-agent-bench)).

## Deadline and recovery comparison (proposed)

Use two separate fault fixtures so the comparison distinguishes a slow page from a transport that never completes. First, serve a local page with a deterministic delayed response and run a bounded navigation/read operation with a caller deadline; record elapsed time, typed error, whether the process/session remains usable, and whether a post-deadline mutation occurs. Second, use a local CDP endpoint that accepts a TCP connection but never completes the WebSocket upgrade; bound connection setup externally at a short, fixed deadline. Record whether each interface returns before the deadline, whether its CLI/daemon/browser descendants remain alive, and whether the next normal session can recover. Use OS process-tree inspection for cleanup, not only the caller's exit status. For Scout, cover Go, CLI, and MCP separately, since a Go context deadline does not prove that every adapter propagates it. For competitors, use each documented timeout control and report unsupported controls as unsupported. Pin release and browser versions, capture raw output and process IDs, repeat at least ten times with a fresh process/session per run, and report median/p95 plus cleanup success. Agent-browser issue [#1713](https://github.com/vercel-labs/agent-browser/issues/1713) remains open and follow-on [PR #1851](https://github.com/vercel-labs/agent-browser/pull/1851) proposes a 30-second handshake bound and recovery; rerun against a released fix before publishing comparative results. A wedged endpoint is not a substitute for exercising cancellation during a real browser command.

Scout v28 has focused deadline probes. The Go CDP transport probe returned at its 250 ms context deadline in 251 ms. The real MCP stdio probe set a 300 ms watchdog, sent `navigate` to a silent remote CDP endpoint, required `SCOUT_TIMEOUT`, observed the handshake socket close within 750 ms, then successfully called `list_sessions`. Ten fresh-process MCP repetitions passed 10/10; request duration median was 301.6 ms and p95 was 302.8 ms. Timing excludes MCP process startup; the endpoint and client used loopback. This verifies deadline propagation into the remote handshake and server responsiveness in this fixture, but not browser-command cancellation, goroutine/process-tree cleanup, or competitor behavior. The full v28 harness did not complete in the available run, so no full-suite status is claimed.

The focused `late-action-cancellation` browser case uses a click handler that signals dispatch, blocks the page main thread for 1.2 seconds, then mutates the DOM and signals completion. The first local Chrome run returned `outcome_unknown` after 401 ms for a 300 ms caller deadline. That exposed a 100 ms URL read in unknown-outcome reporting after the deadline. Scout now skips that post-deadline browser read both when constructing the action error and in shared trace failure handling. Ten fresh-browser runs returned in 300.1–302.3 ms (median 301.7 ms, p95 302.3 ms); all ten returned before the completion signal and later observed `Late completion` in the DOM. Unknown click errors retain their expected postcondition; Go's `ReconcileActionOutcomeContext` and MCP's read-only `reconcile_action` verify it on the original target without repeating the click. The benchmark confirms a late completion reconciles as `postcondition_verified` and a changed target is refused as `stale_target`. The per-run evidence is preserved in [`scout-late-action-cancellation-10x-2026-11-06.json`](results/scout-late-action-cancellation-10x-2026-11-06.json). Reproduce with ten separate runs of `SCOUT_BENCHMARK_FOCUS=late-action-cancellation go run ./examples/benchmark`, then aggregate the JSON files with `go run ./examples/benchmark/report`. The caller must not infer “not executed” from a timeout. This is repeated evidence for Scout's Go API on local Chrome, not a broad timing guarantee or proof that JavaScript can be canceled. CLI errors serialize the expected postcondition, and the stateful JSONL CLI now returns a portable record that a second `reconcile` request verifies without replay; the end-to-end test is [`close_recovery_integration_test.go`](../../cmd/scout/close_recovery_integration_test.go). This CLI close-tab case is a separate fixture from the late-click comparison below.

`SCOUT_BENCHMARK_FOCUS=mcp-http-shared-remote-ownership go run ./examples/benchmark` isolates that remote-browser boundary. It starts one Scout HTTP server with `SCOUT_REMOTE_CDP` pointed at an externally launched disposable Chrome, initializes two HTTP clients, and seeds a same-origin cookie and `localStorage` value through the first client. In a 6 November 2026 run, the second client navigated the same target, observed the first client's values, then wrote secondary values which the first client observed. Both calls returned the identical target ID. The focused probe completed in 3.75 s (5 tool calls, 2,815 response bytes); its raw report is [`scout-mcp-http-shared-remote-ownership-2026-11-06.json`](results/scout-mcp-http-shared-remote-ownership-2026-11-06.json). This establishes current shared-state behavior for this local Chrome configuration. It does not exercise unauthorized cross-owner calls, target closure, or an owner-bound policy, and is not a competitor comparison or multi-tenant guarantee. The near-term deployment opportunity is a trusted gateway that routes each authenticated principal to a dedicated Scout process and browser endpoint; the current server accepts one process-wide `SCOUT_REMOTE_CDP` and its optional bearer token is shared, not principal-aware. A native shared service would need stable gateway-verified principal identity separate from `Mcp-Session-Id`, trusted endpoint resolution, and owner-bound cleanup before it could safely offer shared authenticated profiles.

`SCOUT_BENCHMARK_FOCUS=mcp-http-delete-cleanup go run ./examples/benchmark` starts a locally owned browser over Streamable HTTP, captures the server-minted MCP session ID, sends protocol `DELETE /mcp`, and checks that the newly launched Chrome process exits. Four fresh runs on 5 November 2026 passed 4/4; each returned HTTP 204 and observed the owned Chrome process exit in 1.58–4.58 s. This verifies the normal DELETE cleanup path with a process-level signal. It does not test a disconnect without DELETE, a process crash, a long-running in-flight action during DELETE, or remote-CDP ownership.

`SCOUT_BENCHMARK_FOCUS=mcp-http-idle-stream go run ./examples/benchmark` starts two independent HTTP clients with a 1.6 s idle timeout, opens an SSE stream for each, and sends repeated status calls only through client two. Client one's browser must expire while its stream remains open; client two's browser must remain alive. The fixture then navigates again through client one and requires a distinct target, proving its default session was recreated inside the same client namespace. Three fresh runs on 5 November 2026 passed 3/3. A 6 November focused rerun also passed: client one's Chrome process exited, client two's process remained alive, and client one restarted into a distinct target. This is a Scout contract check, not a matched competitor benchmark.

`SCOUT_BENCHMARK_FOCUS=mcp-http-idle-inflight go run ./examples/benchmark` adds the complementary HTTP case: one HTTP client keeps an SSE stream open while a `wait_for` runs longer than the idle timeout with no other MCP tool calls. A matched 1 s timeout / 1.8 s delayed-element run then passed 10/10 with wait durations 1.779–1.838 s, each browser staying started through the call and returning to lazy state after the handler returned and the idle window elapsed. Reproduce the repeated matched Scout run with `SCOUT_BENCHMARK_FOCUS=mcp-http-idle-inflight SCOUT_BENCHMARK_REPEATS=10 SCOUT_BENCHMARK_IDLE_TIMEOUT=1s SCOUT_BENCHMARK_WAIT_DELAY_MS=1800 go run ./examples/benchmark`. The matched Playwright MCP comparison uses `node examples/benchmark/compare_playwright_inflight_idle.mjs http://127.0.0.1:41743 0.0.84 10 1000 1800`, with the local fixture server on port 41743. All 10 runs failed: `browser_wait_for` returned at 1.011–1.022 s with “Target page, context or browser has been closed.” Scout passed 10/10 for the same 1 s idle timeout and 1.8 s wait. Both used Streamable HTTP, isolated headless Chrome, and the same delayed-element predicate. Playwright’s current documentation says the idle timer does not fire while a tool call runs, so this pinned package behavior contradicts its documented contract; GitHub issue [#42693](https://github.com/microsoft/playwright/issues/42693) reports the same failure class and was closed as not planned. The npm registry reported 0.0.84 as the current package version on 6 November 2026. This is strong evidence for a Scout lifecycle advantage under deliberately short idle limits, not a broad product reliability estimate. The Playwright adapter does not yet check cleanup after completion or saved-state effects. The Scout runner was corrected to launch a direct temporary CLI binary; earlier repeated probes that killed a `go run` wrapper could leave its compiled MCP child running.
