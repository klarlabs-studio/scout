# Scout product vision

The current market-facing opportunity to validate is summarized in the [opportunity brief](opportunity-brief.md). It frames host-owned task continuity as a hypothesis and separates repository evidence from buyer and comparative evidence.

## Competitive read (10 November 2026)

Session controls are no longer a defensible lead: Playwright MCP v0.0.84
documents named isolated contexts, persistent profiles, extension attachment,
and configurable capabilities; agent-browser has a broad CLI/MCP/session
surface and an open PR proposing a fix for the server-pinned session override;
Stagehand has an official Go SDK. The current [capability map and evidence
limits](competitive-opportunities.md#capability-map-and-positioning-consequence-6-november-2026)
lists what Scout must match and what remains unproven.

**Release check (10 November 2026):** agent-browser v0.42.0 adds experimental
saved flows that record a successful request/command path and try direct HTTP,
page-request, then recorded-command tiers. The published flow work includes
explicit write approval and does not resend a write after acceptance or an
ambiguous response. This makes repeated-work reduction and within-flow
lost-acknowledgment handling a stronger competitor baseline; Scout must not
claim either alone as its advantage. Test separately whether a Go host can
preserve its own operation identity across process loss, reconcile against
authoritative business state, and retain evidence for that decision. The
30-pair local probe found fixture parity: both the saved flow and Scout
completed their respective no-resend/reconciliation predicates in 30/30 runs
(Wilson 95% interval 88.6–100%); their HTTP and browser-click dispatch paths
differ. This supports repeatability on this fixture, not comparative reliability
or integration-cost claims. The
current release does not document that host contract; this scope reading is
not a claim of incompatibility or superiority. Keep the CLI/MCP flow arm
separate from the direct Go SDK adoption gate. See the dated [competitive
refresh](competitive-opportunities.md#competitive-refresh-saved-flows-add-a-replayworkflow-baseline-10-november-2026).

**Identity-drift check (10 November 2026):** agent-browser v0.42.0 fixes
session reuse/relaunch after failed attachment. An open silent-browser-swap
report reproduces only on 0.33.2/0.37.1, so rerun it on the current release
before making a claim. Its separate open MCP issue #2422 describes a caller
session argument overriding server ownership; PR #2430 proposes scoping the
argument and remains unshipped in the tracker snapshot. Scout's opportunity is
to make identity drift a task invariant: owner, browser generation, target, and
policy must still match before a task can continue or report completion. Add
this fault to the comparative conformance suite. See the [identity-drift
refresh](competitive-opportunities.md#competitive-refresh-silent-browser-replacement-is-an-identity-test-10-november-2026).

**Competitive status recheck (10 November 2026):** agent-browser v0.42.0
ships experimental saved flows and improves attach/relaunch behavior, while
the MCP server-pinned-session issue #2422 and proposed fix #2430 remain open.
The PR reports focused regression coverage, but the release does not include
that fix. Stagehand's false-green doctor report #3359 remains an open,
version-sensitive diagnostic case; Browser Use #6295/#6298 remain upstream
same-session recovery activity. Measure durable host operation identity and
authoritative reconciliation separately from session continuity and saved-flow
replay. See the dated [status recheck](competitive-opportunities.md#competitive-status-recheck-saved-flows-ship-ownership-fix-remains-proposed-10-november-2026).

Playwright MCP v0.0.85 also changes the attached-browser parity bar: its
extension can leave tabs in their existing groups, remain in the background,
and restrict locator matches to visible elements. Measure these operator-facing
session behaviors separately from task recovery. The active Stagehand Go module
in the monorepo's v4 line still resolves to v4.3.0; the separate official
`stagehand-go/v3` line remains active at v3.21.1, released 23 October with a
local-server security update. The open monorepo release PR for TypeScript
4.4.1 is not a Go SDK release signal. The study deliberately pins v4 for its
protocol-first local direct-page API and must not call v3 archived. See the
[10 November research refresh](competitive-opportunities.md#competitive-refresh-extension-workflows-preserve-more-operator-context-10-november-2026).

The product bet is the **host's outcome decision after browser work is
interrupted**. Scout should make one execution record explain the intended
task and deadline, owner/session/target/policy binding, dispatch boundary,
browser-visible verification, uncertainty, authoritative host reconciliation,
and replay decision. The host remains responsible for business truth; Scout
must preserve that distinction and make the resolution inspectable across the
Go API, CLI, and MCP. This is a direction to validate, not a claim that the
current record is already consistent across all surfaces or that customers
prefer it.

**Category shift (10 November 2026):** Browser Use 1.0.0/1.0.1 is now an
opinionated Python agent and cloud-browser/model platform, with local Chromium
and CLI/MCP operation also available. Its release highlights a persistent
Python REPL over CDP, typed results, domain controls, sensitive-value
redaction, and run workspace isolation. This raises the bar for convenient
end-to-end agents and weakens any claim that local execution or model choice is
unique to Scout. Keep Scout focused on deterministic embedding in Go hosts and
the operation contract those hosts own: durable task identity, positive page
verification, fail-closed retry, and authoritative application reconciliation.
Test Scout against Browser Use's pinned local CLI/MCP path as well as its
cloud-agent path, keeping tool-only and agent-run measures separate. The
release's own benchmark is vendor evidence, not a matched Scout comparison.
See the [dated competitive assessment](competitive-opportunities.md#competitive-refresh-browser-use-10-changes-the-category-boundary-10-november-2026).

**Host-restart comparison (10 November 2026):** the pinned Browser Use
`--cli-mcp` path was extended beyond MCP-only restart. In ten completed local
trials, a distinct host worker reopened a caller-authored SQLite operation
checkpoint after the dispatch worker and MCP process were killed post-commit,
reconnected to the still-running Chrome page, and reconciled the application
ledger with one effect and no replay (10/10). This shows that the host contract
can be composed around Browser Use; it does not show native task persistence,
browser-process recovery, or a Scout advantage. Scout's native task-store
fixture also passes, but comparative integration effort and operator value
remain unmeasured. The next decision depends on the planned participant study,
not another fixture-only pass. See the host-restart report (local audit artifact)

The shared `recover_task_run` view now returns bounded, non-authorizing
guidance from the durable cursor on Go, stateful CLI, and MCP. An initial
cursor is not treated as proof that no action was dispatched: custom stores
without per-action progress may retain it after dispatch. Recovery therefore
requires confirming that the old worker stopped, rechecking target and policy,
and reconciling authoritative application state before follow-up work. This is
implementation progress, not yet a substitute for the cross-surface injected-
failure matrix below.

**Live MCP action-recovery probe (10 November 2026):** the focused `mcp-recovery-record` benchmark passed against a local Chrome and fixture in 21.4 seconds. It verified typed `isError`/`_meta` for uncertain outcomes, late-effect reconciliation on the original target without replay for click variants, typing, upload, batch, submit, select, and hover, retained postconditions/trace linkage, and rejection of 5/5 stale-target reads. This demonstrates action-level reconciliation in one live MCP process. It does not test Scout process loss, task-run recovery through Go/CLI/MCP parity, or task-run recovery after browser replacement; those remain separate gates.

The raw run is `recovery-run-20261110T2214Z-go1.26.0.json` (local audit artifact). This strengthens the local engineering evidence for durable host reconciliation. The ledger is a controlled fixture, so this still does not prove production adoption, customer value, or a comparative advantage.

### Near-term validation sequence

Keep the vision grounded in a short sequence of falsifiable steps:

1. Recruit 5–8 recent browser-worker operators and complete the incident
   interviews before showing Scout. The target is a concrete, recent costly
   ambiguity with a named owner and evidence source, not agreement with our
   vocabulary.
2. Run the paired deterministic Go task from clean checkouts. Measure first
   verified result, full-task effort, integration code, owner/session/policy
   wiring, and the post-commit interruption outcome. Preserve raw task records,
   source manifests, fixture ledgers, and independent grades.
3. For each control-competent pair, require one accepted effect, an `unknown`
   state after worker loss, an authoritative host read before resolution, and
   no replay. Report the actual operator steps and whether host resolution is
   equally simple in both products.
4. Only after the Go task establishes value, run the same task-record contract
   across Go, CLI, and MCP, including replacement process, replacement
   browser, unavailable ledger, and identity drift. A recommendation may say
   to inspect or reconcile; it must never infer retry safety from browser
   evidence alone.
5. Choose the product lead from the study gates in
   [adoption-study.md](adoption-study.md). If recovery pain or comparative
   value fails its gate, use the incident evidence to select first-success,
   diagnosis, or MCP integration as the next bet.

The current readiness gate is still unmet: fixture rehearsals are technically
useful, but the evidence audit finds no participant-attested sessions. The
next product decision therefore depends on recruitment and observed clean-
checkout sessions, not another fixture pass.

## Adoption evidence gate (6 November 2026)

The current repository establishes technical behavior in fixtures but contains
no recorded buyer interviews or independent Scout/competitor onboarding study.
Do not present the Go-native recovery position as validated demand. The next
research step is a 5–8 person study of engineers who have operated browser
workers recently, combining incident-based interviews with a paired Scout and

agent-driven runs separate, and let evidence change the product position: if

effort, reposition around the problem participants actually prioritize.

## Opportunity portfolio and next decision (10 November 2026)

Treat recovery as the lead hypothesis, not the assumed destination. Scout has
three plausible product jobs; current repo evidence supports technical
feasibility only. The adoption study should identify which job is urgent before
Scout invests in a dashboard, hosted control plane, or broader agent surface.

Use the next study to score each bet on (1) recent observed pain, (2) a named
owner and near-term change trigger, (3) successful independent first use, and
(4) a measurable advantage versus the participant's current alternative.
Keep the existing recovery thresholds for promoting recovery. Do not promote
the other bets from interview enthusiasm alone: require at least four of five
evaluable participants to complete the relevant task and a paired measure that
beats the current alternative on either time/effort or preference for a
specific workflow reason. Report small-sample results as directional evidence.
If no bet clears both pain and task-value gates, keep the product thesis open
and recruit more operators instead of picking the most polished implementation.

Sequence the research to avoid conflating different jobs: (1) conduct the
incident interviews without pitching Scout; (2) run the deterministic Go
first-success and recovery task against Stagehand Go; (3) use interview results
to choose whether a distinct MCP study is warranted; (4) validate diagnosis in
a clean container with intentionally broken endpoint, policy, and store
configurations. Record the observed job, participant evidence, task result, and
decision separately. The local recovery reports are useful test-fixture
evidence; they do not count as participant outcomes.

## Competitive direction: explicit browser-session identity (6 November 2026)

### Keep browser restoration separate from task recovery

Agent-browser now offers stable worktree-scoped session IDs, namespace
isolation, cookie/localStorage restoration, and restore validation across
browser restarts ([merged session-hardening PR #1486](https://github.com/vercel-labs/agent-browser/pull/1486),
[session guide](https://agent-browser.dev/sessions)). This is a useful
continuity feature and should be treated as parity. Reopening an authenticated
browser is not proof that an interrupted mutation completed. Scout's session
handle therefore continues to bind to the exact live browser generation and
target; after browser replacement, a prior task remains unresolved until the
host checks its authoritative application state. If Scout adds host-managed
state restoration, it must mint a new browser generation and preserve the
separate, non-replayable task-reconciliation step. Cookie/state storage also
needs an explicit secret-handling contract; agent-browser's docs warn that
saved state contains plaintext tokens.

The next comparative experiment is a delayed, non-idempotent mutation across
worker and browser loss. Grade restored identity, target-generation change,
credential exposure, duplicate effects, outcome classification, and operator
steps separately. See the [competitive opportunity and experiment details](competitive-opportunities.md#competitive-refresh-restored-browser-state-versus-task-continuity-6-november-2026).

### Restart-recovery contract

Session recovery across a Scout process restart must be owner-controlled and
fail closed. Persist only a server-minted opaque handle, an authenticated owner
scope, a logical session name, the browser-instance fingerprint, the exact
DevTools target ID, an optional opaque remote BrowserContext ID, and a versioned
policy digest. Never persist CDP URLs, bearer tokens, cookies, page content, or
other credentials in the session registry. The endpoint and current
origin/egress policy must come from the server's current trusted configuration
after authentication; reject a resume when the owner mapping or policy digest
no longer matches. The BrowserContext ID is sensitive browser state: the
current bbolt file is owner-only but is not encrypted at rest.

On resume, attach with the current trusted endpoint and persisted target and
context IDs, then compare Scout's current `BrowserInstanceID` with the stored
fingerprint before exposing the session. Shared and Scout-isolated remote
contexts are supported; local browsers and Scout-managed proxy sessions are
not. The remote browser must remain alive with the recorded target and context.
A missing target or context, changed browser fingerprint, changed policy,
malformed record, or expired owner authorization must return a non-enumerating
recovery failure and must never create a fresh browser under the old handle.
Explicit owner revocation and default-session close dispose recorded isolated
contexts through the currently trusted remote endpoint before removing handles; failed cleanup retains records for retry. The MCP expiry sweeper leases each expired record, disposes preserved contexts through the principal's current trusted endpoint, then completes the claim; failed cleanup releases the lease and retains the expired record for retry.
Session records share the existing bbolt database transaction boundary with
task-run records. The database file is not encrypted at rest.

Acceptance requires restart coverage with the browser left alive, target or
context closed, browser restarted at a different endpoint fingerprint, owner
changed, policy changed, record truncated, and two principals attempting each
other's handles. Include concurrent resume attempts, close racing with resume,
task-run namespace continuity, and cleanup after authorization revocation.
Compare recovery success, setup steps, and failure diagnosis against Playwright
MCP and agent-browser using the same persistent browser fixture. The Go API can
resume a live shared remote target or isolated remote context after Scout
process restart. It mints a 192-bit opaque recovery handle and persists the
owner, session name, browser fingerprint, exact target, optional BrowserContext
ID, policy digest, and timestamps, then reattaches through the host's current
trusted endpoint and verifies browser, target, and context before returning the
session. This does not recover a browser that has itself restarted, a closed
target/context, local browsers, or Scout-managed proxy sessions. Concurrent
resume, close/resume races, malformed-record fault injection, expiry cleanup,
and comparative setup/failure measurements remain open.

**Implementation update:** the existing bbolt task-run database now also creates a
`scout_sessions_v1` bucket. Its recovery-record API validates a versioned
allowlist of identifiers and timestamps, hides foreign-owner handles as
not-found, supports owner-only revocation and expiry cleanup, and persists no
endpoint or credential fields. Close/reopen and owner-isolation checks pass.
The Go API's live exact-target resume now uses this store and has a Chrome
close/reopen integration check. The stateful CLI exposes `persist_session`,
`resume_session`, and `revoke_session` over JSONL when `--task-store` and a
shared remote CDP endpoint are configured; its owner scope is the local OS
user. MCP now exposes the same lifecycle in the `admin` profile for
authenticated configured HTTP principals, using the principal's stable scope
and trusted endpoint/policy. MCP's ordinary `session_id` selectors remain
same-process only; durable recovery handles are separate records.

Scout's MCP routing keeps HTTP session registries separate by transport and configured principal; stdio uses one process-wide registry. Middleware binds each browser call to the session and target active when that request begins, which prevents a later switch from redirecting an in-flight action. The stateful server accepts per-call names and opaque IDs, so concurrent calls can route to different sessions without mutating the active pointer. Authenticated HTTP clients can reconnect with a new transport ID and select the existing session using its opaque ID while the server process remains alive. The registry and ordinary browser sessions are still in memory; durable recovery is a separate opt-in handle workflow for a principal's configured shared or isolated remote session. The latest MCP specification expects stateless requests to carry metadata needed to recover cross-request state ([statelessness](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/basic/index.mdx#statelessness)).

The stateful selector now accepts either a legacy session name or a server-issued 192-bit opaque `session_id` from `create_session` / `list_sessions`. IDs resolve only inside an authorized owner scope and are revoked on explicit close, idle expiry, or HTTP transport deletion. Authenticated HTTP clients may select the same principal's session by ID after reconnecting with a new transport ID; opaque IDs remain unavailable across principals and to unauthenticated replacement transports. This is same-process reconnect only: MCP IDs and browser registry entries are in memory and stop working after server restart. Explicit selection does not change the active pointer; omitted selectors preserve legacy behavior. `status` accepts either selector form. The live authenticated HTTP principal-isolation benchmark passes same-principal reconnect, live in-flight task-plan/cursor lookup, completed task lookup, and foreign-principal opaque-ID denial in 3/3 fresh runs; it leaves the original server registry alive and does not cover process restart. Browser snapshots and oversized response artifacts are bound to the selected session, with cleanup on close, idle expiry, transport deletion, and shutdown. A single request-scoped routing record carries owner, canonical session key/ID, resolved browser session, and explicit-selection state through tool dispatch. Durable recovery is now available through separate admin tools for authenticated configured principals. An initial stateless Streamable HTTP prototype is available behind `SCOUT_MCP_HTTP_STATELESS=true`; see the validation boundary below.

**Routing audit update (10 November 2026):** owner-level `status`, `reset`, and `clone_session` bind to the session captured at request entry. The repeatable local race fixture holds the session operation lock on a delayed page wait, queues each owner tool, then switches the active pointer. Ten fresh-process runs passed 10/10: clone copied the captured source, status returned the captured target, reset applied to the captured session, and the newer switch plus right-session target were preserved. This closes those local stdio fixture assertions; it does not cover authenticated multi-client HTTP routing, external tab churn, or all owner-level operations. See the command and exact predicates in the benchmark README.

The selector is an address, not a credential. Never derive authorization from a caller-provided session name alone. For authenticated HTTP deployments, bind the registry entry and durable task-store namespace to principal plus opaque session ID. For stdio, an opaque ID still enables concurrent tools but only within that process; reconnect recovery requires a durable server-side owner identity and an explicit policy for who may resume it. Avoid changing the implicit active pointer when an explicit selector is present, or concurrent calls can race through otherwise isolated sessions. Configuration tools that currently mutate client-wide defaults need a declared scope: process/server, owner, or individual browser session.

The opt-in stateless HTTP mode uses `WithStreamableStateless()` and requires configured principal authentication, since the transport has no client session ID to scope the registry. Middleware reads the caller-carried opaque Scout session handle from decoded `_meta`; browser/session-scoped calls fail closed without a valid handle. `SessionStore` remains transport protocol state and does not replace Scout's browser registry. Owner-level configuration and lifecycle tools remain principal-scoped, and the registry relies on explicit close or idle expiry because stateless HTTP has no transport `DELETE` cleanup callback. Chrome-backed integration covers foreign-principal denial, reconnect, concurrent session routing, close/revocation, task-store and snapshot ownership, quota cleanup, idle/in-flight behavior, cancellation, and graceful single-process restart. Independent TypeScript and Python SDK smokes create a browser session, navigate, read page content through its opaque handle, cancel an in-flight wait, read again, and close it. CI runs both Go integration and SDK smokes. Multi-replica load balancing, OAuth, and additional client SDKs remain open; keep stateful HTTP as the default until those deployment and compatibility cases are covered.

The tool-scope inventory, owner-scoped opaque-ID registry, session-specific snapshot/response-artifact ownership and cleanup, and canonical request routing record are implemented. Same-process MCP reconnect by opaque ID is live-tested; a durable task record is also retrievable after transport replacement when the same principal and session are selected. The Go API, stateful CLI, and MCP admin profile can persist a recovery handle and resume an exact live remote target; isolated remote contexts are also recoverable after a Scout process restart. The authenticated MCP restart fixture covers simultaneous resumes, close/resume races, and foreign-principal denial. The bbolt store treats malformed JSON handles as unavailable/no-op for lookup and revoke. MCP expiry cleanup disposes isolated contexts only after verifying the configured endpoint's browser fingerprint. The bbolt cleanup sweep now skips already-attempted records within one pass, continues after an individual cleanup failure, releases that claim for retry, and retries on a one-minute interval. The owner/session task-store adapter now forwards the optional atomic handoff, plan, and cursor persistence interfaces, preserving the pre-dispatch handoff boundary for MCP backed by bbolt. Remaining gaps: prove cleanup behavior across browser outages and multiple MCP replicas, align other resources and lifecycle operations with the canonical routing record, validate multi-replica load balancing, and test mixed explicit/implicit calls without cross-routing. A Chrome-backed stateless restart regression passes: pre-restart handles are denied and a fresh handle works after restart. Chrome-backed stateless tests cover same-principal session task/artifact isolation and cleanup. The independent TypeScript and Python SDK flows cover session-bound browser actions, cancellation of an in-flight wait, and a successful read after cancellation.

This is a competitive hypothesis, not a shipping claim. It would make Scout's existing safe-action receipts, target pinning, and task recovery usable by parallel and reconnecting workers without a mutable “active session” convention. Compare the new mode with current stateful Scout, Playwright MCP isolation modes, and agent-browser named sessions on cross-routing, reconnect success, setup steps, schema/context cost, cleanup latency, and failure diagnosis before promoting it as an advantage.

**Stateless implementation gate update (10 November 2026):** inspection of the pinned `go.klarlabs.de/mcp` v1.30.1 source confirms stateless Streamable HTTP drops the transport session lifecycle and requires `Mcp-Method`; the protocol `SessionStore` does not persist Scout browser state. The prototype uses configured principal authentication as a stable registry owner and requires the opaque Scout handle in `_meta` for browser/session-scoped calls. A live local Chrome fixture confirms discovery, owner-scoped handle issuance, successful navigation and same-handle target continuity across independent requests, and parallel navigation through two handles to distinct targets. Missing/named, unknown, unauthenticated, and foreign-principal selectors are rejected before browser access. This is one run; repeated concurrency, durable task/artifact namespace isolation, and cleanup under disconnect or browser failure remain open. The in-memory registry relies on explicit close or configured idle expiry because transport `DELETE` is absent. Keep production claims gated by the fuller matrix in [competitive opportunities](competitive-opportunities.md#mcp-stateless-transport-compatibility-6-november-2026).

**Tool schema follow-up (10 November 2026):** exposing the selector as an ordinary `session_id` tool argument is not a middleware-only change. The pinned MCP server generates closed schemas from typed inputs, validates arguments before invoking handlers, and its public `Server.Use` middleware cannot intercept tool-list results. A request-only rewrite would therefore be rejected by clients or strict validation. Keep the namespaced `_meta` selector as the supported stateless prototype interface until a dependency API or explicit tool-schema implementation can advertise and consume a typed argument. Any implementation must reject conflicting selectors and preserve the existing authenticated owner-to-session resolution; the handle remains an address, never an authorization credential.

## Implementation update: portable task recovery handoff (6 November 2026)

The durable recovery example now verifies the selected Chrome target from an independent `agent-browser` 0.41.2 process attached through CDP discovery. It compares the peer's stable `targetId` and page URL with Scout's live observation before accepting the handoff. The example uses `npx` by default; set `SCOUT_AGENT_BROWSER_BIN` to an installed compatible CLI and optionally `SCOUT_AGENT_BROWSER_VERSION` to select the package version. This proves target agreement for the demo's top-level page, while owner scope, browser generation, and policy identity still come from the trusted host/broker and Scout session. It does not by itself authenticate an arbitrary peer adapter.

The receiving host process now reads the fixture's independent `/ledger` endpoint before recording `verified_complete`; it checks the count expected for that task and rejects a mismatch. A fresh `go run ./examples/durable_task_recovery` completed both Scout process-loss boundaries and full browser replacement, reporting authoritative counts 1, 2, and 4 while same-task retries remained blocked. This is a runnable local-fixture demonstration of host-supplied evidence, not evidence for a production ledger or cross-vendor receipt import.

`TaskRunRecord` now carries a versioned `TaskRunPlan` containing action names, selectors, postcondition kinds, target identity, deadline, and policy metadata, but omits action inputs and expected text/values. The bbolt store atomically persists browser/target binding, this redacted plan, and the initial cursor before dispatch, closing the pre-dispatch gap where an interrupted reservation could lack the plan needed by a recovery host. MCP `get_task_run`, stateful CLI lookup, and Go lookup expose the plan. It is descriptive evidence only and cannot be replayed; hosts still reconcile with authoritative application state. Existing custom stores remain compatible; they can implement `TaskRunHandoffStore` for atomic persistence. Focused checks cover redaction and bbolt close/reopen persistence.

## Implementation update: portable recovery receipt export (6 November 2026)

The `scout.recovery-receipt/v1` envelope now has a Go type, strict decoder and validator, and adapters for retained task records. ## Product direction update: auditable outcome handoff (6 November 2026)

Session restore and strict target pinning are now competitor capabilities, so
Scout should treat them as baseline continuity requirements. The stronger
product claim is a target-bound recovery record plus an explicit host decision
after the browser cannot prove whether a mutation committed. Resolution records
can now retain the host's evidence source, opaque source reference, and
observation timestamp alongside its status and short evidence note. These
values remain host attestations: Scout does not verify an external ledger or
claim that it did.

The next validation should follow the record across distinct runtimes, not only
Scout processes: one sender exports and signs the receipt, a receiver obtains
live target and policy identity from its own browser adapter, and the host
checks the same authoritative app ledger before recording resolution. Measure
false-complete and duplicate effects, receipt redaction and portability,
recovery time, and integration code. Until the receiver adapter and buyer
workflow are validated, position evidence provenance as an integration aid,
not a proven competitive advantage.

Cross-runner matching also requires an explicit frame-observation flag. This
prevents an adapter's missing frame identity from matching the receipt's empty
top-level-frame ID by default. A receiver may set the flag only when its
browser adapter confirms which frame is selected. The receiver observation now
has a strict JSON schema and decoder, giving non-Go adapters a stable input
shape while leaving authentication and broker mapping with the host.

**Broker observation contract (6 November 2026):** `agent/recovery_handoff.go`
now defines `scout.recovery-observation/v1`. A trusted browser broker can sign
its live owner, browser generation, target, frame, and policy binding with
Ed25519; receiving runtimes verify with a public key and reject expired,
future-dated, malformed, or over-two-minute observations. The combined
comparison verifies both the sender's HMAC receipt and the broker's signed
observation, while keeping `ReplayAllowed` false. This establishes an
interoperable verification primitive and is verified by a separate Node.js
receiver in the recovery example. The example still feeds fixture-supplied
owner/generation/policy fields and an unauthenticated agent-browser target
observation; production broker integration, key distribution/rotation, and
frame-capable peer evidence remain open. See the
latest recorded run (local audit artifact).

## Implementation update: oversized MCP result artifacts (6 November 2026)

When a successful tool result or JSON-RPC error exceeds the 256 KiB MCP response cap, Scout now stores the serialized result/error as a mode-0600 JSON artifact and returns its path, byte count, MIME type, and SHA-256 in the limit envelope while preserving the original error code. Artifacts are bound to the requesting MCP principal/session; other clients cannot read, search, or delete them. The read, search, and delete tools are included in every MCP profile, so an overflow reference remains recoverable in `core`, `read`, `interact`, `diagnose`, and `admin`. Automatic saves are bounded to 16 MiB per response, 4 artifacts/32 MiB per client, and 32 artifacts/64 MiB total per MCP server process; responses beyond those budgets remain omitted with a recovery hint that reports why saving failed.

## Implementation update: verified task run contract (6 November 2026)

The Go API `Session.RunTaskContext`, MCP `task_run`, and stateful JSONL `task_run` now wrap batch execution in a task-level result with a caller task ID, pinned target, whole-run deadline, positive verification requirement, optional final page-state postcondition, status (`completed`, `rejected`, `needs_reconciliation`, or `incomplete`), and `resume_from` index. A failed final postcondition uses `needs_reconciliation` with `failure_reason: verification_failed` and keeps same-ID replay blocked until host reconciliation. The final condition runs only after all actions finish on the original target; an incomplete or uncertain batch remains incomplete or uncertain. Existing action receipts and portable recovery records remain nested in the batch result. MCP checks that its active profile exposes `recover_task_run` and `resolve_task_run` before every `task_run`; `required_tools` can declare additional follow-up capabilities. A session-scoped idempotency registry binds each task ID to a plan fingerprint and stores its result: identical retries return the saved result without replaying actions and mark the returned result with `idempotency_replay: true`, while concurrent use or a different plan with the same ID returns `SCOUT_TASK_ID_CONFLICT`. The registry retains up to 256 IDs and returns `SCOUT_TASK_CAPACITY` before browser work rather than evicting records. After reconciling an uncertain action, callers decide whether to retry it or continue, then use a new task ID for the chosen plan. `SessionConfig.TaskRunStore` now allows a host to persist reservations and results using its own database; persistent stores must atomically reserve IDs and fail closed on interrupted reservations. Scout now includes an optional bbolt-backed durable store for a single-process owner; focused close/reopen checks confirm completed results remain reusable, interrupted reservations remain bound and are not recreated, and conflicting plans fail closed at the store boundary. MCP and stateful CLI can opt into it with `--task-store=PATH`; MCP IDs are namespaced by owner and named session so durable results are not shared across principals. The database has one 8,192-record cap and no automatic pruning. Clustered Go hosts can implement the interface with a shared transactional database. The default remains session-local memory, so retries after process loss are protected only when a durable store is configured. A supplied task origin set must exactly match the session's startup `AllowedOrigins`; the task API refuses to imply that it can narrow a policy on an already-running browser. The initial page is checked against that policy, and target identity is guarded through each action. The result reports `session_page_policy` or `no_origin_allowlist` and does not assert proxy coverage. This is the first composable task contract, not full orchestration: per-task policy creation before session launch remains future work. The durable recovery example now kills a process during dispatch and after final page verification but before result commit; fresh processes block same-ID replay and reconcile against fixture state. Ten full-browser-loss probes per peer now exist. Blind UI replay duplicated the harmless fixture effect in 10/10 runs for each; native task-ID guards and matched outcome classification remain unmeasured.

Task-run persistence now binds browser-instance and target IDs to the reserved task before the first action is dispatched. Reservation cleanup runs only when execution has not started; a panic or process exit after dispatch leaves the record in-flight so a retry is refused. Completion and pre-dispatch cleanup use a bounded detached context so caller cancellation does not silently discard the durable outcome. Scout includes a bbolt backend for a single-process owner; clustered hosts still need a shared transactional implementation. The runnable `examples/durable_task_recovery` kills a Scout child after the fixture accepts a mutation but before its response returns, then reopens the store in a fresh process and verifies the persisted `actions/started` cursor. It also kills a second child after the final page condition is verified and the `result_persisting` phase is durable, but before the completed result is stored. Fresh processes reject both same-ID retries before dispatch, reconcile from fixture state, and confirm one mutation per task. A separate task demonstrates cross-process reuse of a saved result. Scout’s crash boundaries run while Chrome and the fixture stay alive. A single full-browser-loss probe each for agent-browser 0.41.2 and Playwright MCP 0.0.84 also kept the fixture mutation count at one after restart, while neither restored the localStorage marker; these peer probes do not test task outcome classification or host-supplied idempotency and need repetition before comparative claims.

**Task record lookup update (6 November 2026).** Go `Session.GetTaskRunContext`, MCP `get_task_run`, and the stateful JSONL `get_task_run` command expose a retained record without mutation. Hosts can inspect a completed result or find the browser target bound to an interrupted reservation. An in-flight record remains ambiguous and requires application-state reconciliation before the host chooses a new plan or task ID. MCP lookup uses the active session namespace; durable lookup across an HTTP reconnect requires the same authenticated principal and named session configuration. The principal-isolation matrix now inspects a live `actions/started` cursor and redacted plan from a replacement same-principal HTTP transport while the task's original call continues, then reads the completed result; it passed 3/3 fresh runs. Uncredentialed HTTP transport IDs and stdio process sessions do not promise stable identity across reconnects or restarts. The durable recovery example exercises lookup from a fresh Scout process after both action-dispatch and post-verification/pre-result-commit termination. Ten full-browser-loss probes now exist for each peer; deliberate blind UI replay duplicated the fixture effect in 10/10 runs each. Native task-ID guard and matched outcome-classification runs remain outstanding.

## Implementation update: MCP deployment origin policy (6 November 2026)

`SCOUT_MCP_ALLOWED_ORIGINS` now sets a startup-only exact-origin allowlist for MCP stdio and shared-token HTTP sessions. Invalid, wildcard, path-bearing, query-bearing, or malformed entries fail server startup. `configure` cannot change the list. Principal-mapped HTTP deployments must use each principal's required `allowed_origins`; Scout rejects combining the global variable with principal mappings to avoid a silently overridden policy. This is a page-layer control for navigation, redirects, and page-target Fetch-intercepted HTTP(S) requests. Service-worker traffic and WebSocket handshakes remain outside that enforcement, and remote browser hosts still need network-level egress controls.

## Implementation update: strict verification for batches (6 November 2026)

Batch callers can now opt into `require_verified` through MCP and the stateful JSONL CLI, or `BatchOptions.RequireVerified` through Go. Before starting browser work, strict mode validates every action, checks each postcondition, and requires positive evidence to be available for every step. During execution, the batch stops at the first step without positive verification evidence and returns the partial result, stopped step, and first unattempted action index. This catches successful dispatches whose application effect was not asserted, as well as rejected and unknown outcomes. Unknown outcomes remain marked for reconciliation. The option is additive and preserves the existing default behavior. This is a caller-selected verification contract for supported batch actions; it does not infer business acceptance, and actions need an explicit postcondition unless their result already includes verified evidence.

## Implementation update: portable recovery is bound to its browser (6 November 2026)

Portable recovery schema version 3 carries a SHA-256 fingerprint of the live DevTools WebSocket endpoint and BrowserContext. Reconciliation checks this identity before inspecting the original target or page state; a missing or different identity returns a structured error and leaves the outcome unknown. A browser-backed CLI integration test creates a delayed click outcome, serializes it, reconnects a fresh Scout session to the same still-running browser, and verifies the late effect without replay. It then closes a separate target in another browser and confirms that browser cannot satisfy the original recovery record. A second live fixture uses two isolated BrowserContexts on one Chrome endpoint: after the source-context target is closed and absent from inventory, the other context still rejects the record. Unit tests also reject absent identities. This action-level recovery record still cannot bind to a replacement browser because the endpoint identity changes. The separate durable task-run store can preserve an interrupted reservation across browser replacement and lets a host record verified reconciliation from authoritative application state; it does not restore the old page or automatically prove the application outcome.

Portable `close_tab` reconciliation now also removes the named tab from Scout's registry after the matching browser target is confirmed absent, but only when the saved tab name still maps to that exact target and is not active. A live fixture serializes and decodes the recovery record, closes the tab through an independent CDP connection, waits for target inventory to report absence, reconciles, and confirms the stale tab entry is gone. This covers late target loss and local registry repair; it does not simulate a `close_tab` call timing out while its CDP close command is in flight.

The timeout case is now exercised through a local WebSocket proxy that forwards `Target.closeTarget` to Chrome but delays its response past the caller's 150 ms deadline. Scout returns `outcome_unknown` with the exact target and `target_absent` predicate; Chrome closes the target before the delayed response arrives; the serialized record then reconciles against the same endpoint and removes the stale named-tab entry. This fixture found and fixed the omission of `target_absent` from the close error's recovery record. The integration scenario passes repeatedly; the proxy models a delayed CDP response while Chrome applies the close promptly, so it does not characterize every real disconnect or browser shutdown timing. Unpersisted isolated contexts are disposed when their owning session closes. Persisting a recovery handle transfers cleanup responsibility to the durable owner: Scout detaches without disposing the context, and explicit revocation or default-session close disposes it through the trusted endpoint before removing its handle. The MCP expiry sweeper now disposes the preserved browser context before deleting the expired record, retaining the record and reporting an error when cleanup fails.

## Implementation update: exhaustive batch evidence counts (6 November 2026)

Batch results now distinguish `verified`, `rejected`, `unverified`, and `unknown` outcomes as mutually exclusive evidence states. Rejected and unknown steps are included in `failed`; successful steps remain counted in `succeeded`, including those whose application effect was not asserted. The response contract is documented in the MCP tool description and README. Focused browser-backed integration cases pass for verified/postcondition-rejected outcomes, unverified successful actions, and ordinary action failures. The distinction lets callers choose whether to proceed, inspect, or retry without inferring evidence quality from `success` alone.

The stateful `scout session` JSONL protocol now accepts the same `actions` array, timeout, and 100-step cap as `execute_batch`. A live browser-backed test expires a two-step batch while waiting on its second selector and confirms the JSONL error response has no success `result` and retains both the verified first step and interrupted second step under `partial_result`. A second test dispatches a click that changes the page, times out during settling, and confirms the partial result carries an `outcome_unknown` recovery record bound to the target and expected text. It then closes the original Scout session, attaches a fresh Scout session to the same externally owned Chrome, and reconciles the exact serialized record against the original target; the late effect verifies without replay. Successful calls return the shared `BatchResult` structure and action receipts. CLI protocol tests also cover action decoding and validation. This proves batch recovery across Scout session/process boundaries when the same browser instance and target remain available; recovery after browser restart or target replacement remains intentionally unsupported.

## Implementation update: batch outputs retain recovery under the MCP cap (6 November 2026)

Batch actions are now limited to 96 KiB of serialized JSON input before session startup or browser access. This bounds caller-controlled selectors and postconditions that can be repeated in recovery records. When a successful or interrupted MCP batch response exceeds the 192 KiB compaction threshold, Scout removes verbose step evidence, semantic field partial results, and duplicate receipts; it retains aggregate evidence counts, step indices/actions/outcomes, and portable recovery records, and marks the result with `truncated` and `truncation_reason`. Interrupted batch error envelopes are compacted in their text form as well. Focused regressions verify both response paths stay below the 256 KiB protocol limit and that the preserved recovery record still validates. `go test ./agent ./cmd/scout` passes. This bounds the serialized MCP contract; peak memory before response construction and end-to-end behavior through every MCP host remain separate measurements.

## Competitive opportunity update

Checked 5 November 2026 against current product documentation and public issue trackers. Public issues are individual reports and must be treated as scenario ideas rather than estimates of defect frequency.

### What competitors already do well

- **Playwright** now spans its cross-browser libraries and testing ecosystem, an agent-oriented CLI, and Playwright MCP. MCP capability groups expose network, storage, testing assertions, tracing, vision, PDF, and devtools; snapshots support subtree/depth limits, search, and file output. Its CLI is explicitly positioned for coding-agent browser workflows and token-efficient operation. A differentiation strategy based on “more browser tools” is unlikely to hold.
- **Vercel agent-browser** emphasizes a CLI and daemon, persistent sessions, batching, semantic refs, snapshots, skills, provider integrations, and configurable output. Its advantage is workflow breadth and a focused terminal interface.
- **Stagehand** is an agent-focused SDK across TypeScript, Python, and Go. It sells self-healing `act`, `observe`, `extract`, hybrid snapshot token efficiency, familiar APIs, batching, iframe locators, and OpenTelemetry. Go support alone is not unique; its local semantic-action quickstart requires a model, while direct page APIs remain available as a deterministic path.
- **Browser Use** pairs browser operation with a full agent loop and hosted cloud execution. Scout does not need to mirror that service category to be useful.

### Further research: where the competitive edge can compound

Checked 5 November 2026 against current documentation and open or recently closed GitHub reports. These reports are signals for benchmark scenarios, not proof of prevalence. Competitors actively fix reported problems, so Scout should compete on a published contract and repeatable evidence rather than on a temporary bug list.

- **Reliability is an implementation race; the opportunity is measurable behavior.** Current agent-browser source probes tabs for a live renderer and revives discarded targets before enabling CDP domains ([target discovery and renderer recovery](https://github.com/vercel-labs/agent-browser/blob/main/cli/src/native/browser.rs#L3712-L3937)). That means Scout should not position renderer revival or target-loss reporting as unique. Agent-browser issue [#1713](https://github.com/vercel-labs/agent-browser/issues/1713) describes unbounded waits; follow-on PR [#1851](https://github.com/vercel-labs/agent-browser/pull/1851) is open, not released, and proposes a 30-second WebSocket-handshake bound plus lock release and retry recovery. Treat this as a timely benchmark lead, not a lasting competitor weakness. Scout's benchmark currently proves a narrower positive contract in one run: remote CDP disconnect during a dispatched click reports `outcome_unknown`, status says recoverable/dead, reset reattaches after browser restart, and a post-reset action verifies; external target closure is separately reported with the target ID through Go and MCP. Focused v28 MCP stdio probes sent `navigate` to a silent CDP handshake with a 300 ms watchdog; ten fresh-process repetitions returned `SCOUT_TIMEOUT` (median 301.6 ms, p95 302.8 ms), closed the client handshake socket within 750 ms, and answered a subsequent `list_sessions` request. The CLI probe found that startup used a separate timeout before navigation; Scout now uses the CLI deadline through session startup and navigation. Ten fresh CLI runs returned a timeout and closed the socket in a median 304.5 ms and p95 309.3 ms for `--timeout=300ms`, and each process exited. These fixtures validate one startup transport failure path, not every tool, browser-command cancellation, goroutine cleanup, or comparative performance. Next, benchmark caller-controlled queue, connect-handshake, browser-command, and cleanup deadlines independently, including late mutation effects and repeated recovery. Publish distributions and cleanup evidence across local and remote browsers before claiming reliability leadership.

- **Session and target identity is a persistent systems problem.** Playwright MCP documents isolated client contexts and warns that persistent profiles cannot be shared by concurrent browser instances; its recent release notes also describe fixes for isolated-client idle cleanup and safer close behavior in shared contexts ([configuration and session docs](https://github.com/microsoft/playwright-mcp), [release notes](https://github.com/microsoft/playwright-mcp/releases)). Playwright MCP issue [#1631](https://github.com/microsoft/playwright-mcp/issues/1631) reported cross-client page bleed and was closed with isolated-context guidance. Playwright issue [#42961](https://github.com/microsoft/playwright/issues/42961) raises a distinct need: per-client page ownership while retaining one authenticated shared profile; it was archived/closed without an upstream implementation commitment. This makes browser identity a product choice between isolated storage and shared credentials with page-level ownership. Agent-browser has reports about active-tab refs invalidated by closing a background tab ([#2407](https://github.com/vercel-labs/agent-browser/issues/2407)) and silent target drift on CDP-attached Edge ([#1867](https://github.com/vercel-labs/agent-browser/issues/1867)); PR [#2396](https://github.com/vercel-labs/agent-browser/pull/2396) merged 5 November 2026 to centralize session-setting reuse/relaunch decisions and report browser relaunches. Stagehand reports include `activePage()` selecting an unexpected tab ([#3371](https://github.com/browserbase/stagehand/issues/3371)). The product opportunity is an explicit session-to-target binding with ownership, active-target evidence, and predictable behavior on close, disconnect, restart, and concurrency. **Current Scout slice:** each MCP browser tool call captures its session and target at request start; page-scoped tools can also assert a caller-provided `target_id`, and Go and CLI APIs expose equivalent assertions. HTTP serving is available through `scout mcp serve-http`; stateful HTTP clients receive separate default and named session namespaces, while stdio retains its process-local registry. A five-run fixture verified stale-target refusal, non-colliding same-name session creation, and refusal to switch to another client's private name. A further matched frame-scope fixture passed through Scout's Go API in 5/5 runs after closing an unrelated tab; agent-browser v0.41.2 failed on the original frame ref in 10/10 runs. Open PR #2408 proposes the upstream fix, so rerun against its released version. The configured remote CDP endpoint remains shared external browser state. Continue testing close/reopen, remote CDP ownership, lifecycle cleanup, and matched competitor behavior before claiming a comparative advantage.
- **Recent issue reports reinforce the identity and evidence bets.** Playwright MCP issue [#1631](https://github.com/microsoft/playwright-mcp/issues/1631) describes cross-client page events causing one client to observe another client’s tab; [#1343](https://github.com/microsoft/playwright-mcp/issues/1343) describes execution staying on a background tab after a new tab opens. Browser Use issue [#5137](https://github.com/browser-use/browser-use/issues/5137) proposes structured before/after action evidence to distinguish changes, no-ops, navigation, and failures; issue [#5252](https://github.com/browser-use/browser-use/issues/5252) reports execution failures returned as ordinary successful MCP results. These reports are useful failure fixtures, not frequency estimates. Scout's outcome records and request-bound target capture align directly with these failure classes. Playwright snapshots also document refs as snapshot scoped and invalid after page changes ([snapshot guide](https://playwright.dev/mcp/snapshots)), making explicit target and frame identity a practical extension of stale-reference handling.
- **Recent PRs show the bar is moving from timeouts to cancellation and identity guards.** Stagehand PR [#2394](https://github.com/browserbase/stagehand/pull/2394) adds cooperative cancellation so a timed-out action cannot continue dispatching later browser commands; already-sent commands still cannot be recalled, so late effects remain a benchmark concern. Stagehand PR [#2439](https://github.com/browserbase/stagehand/pull/2439) validates observed DOM-node identity before acting after rerenders. Agent-browser PR [#1117](https://github.com/vercel-labs/agent-browser/pull/1117) adds isolated CDP browser contexts for separate cookie/storage state, while [#1923](https://github.com/vercel-labs/agent-browser/pull/1923) invalidates refs after document-changing navigation. These changes show that target identity and cancellation are actively addressed across the field; Scout should publish the same failure-mode coverage as a repeatable cross-layer contract, not claim competitors lack the features.
- **Current Scout schema audit:** `target_id` is now accepted by the remaining observation surfaces `auto_extract`, `pdf`, `discover_form`, `wait_for_spa_idle`, and `annotated_screenshot`; handlers pass the assertion through the same request context as other page operations. `hybrid_observe`, `find_by_coordinates`, and `select_by_prompt` return target identity so callers can bind the follow-up action to the page they saw. `ObserveWithBudgetContext` checks the assertion under the session lock instead of bypassing it. Browser integration for stale-target rejection and concurrent tab/session changes remains to be exercised before broad claims.
- **Deadlines and recovery are part of task correctness.** Stagehand reports include a transport deadline that cuts off longer requested waits ([#3369](https://github.com/browserbase/stagehand/issues/3369)) and a network-idle wait that times out when the page is already idle ([#3370](https://github.com/browserbase/stagehand/issues/3370)). Agent-browser issue [#2369](https://github.com/vercel-labs/agent-browser/issues/2369) reports a cold Windows launch timing out while Chrome is still starting. The older launch/connect hang report [#1821](https://github.com/vercel-labs/agent-browser/issues/1821) was closed after fix #2160 shipped in v0.39.3; do not list it as an open current defect. These cases point to a useful Scout product contract: one caller deadline from queueing through browser work, clear cancellation state, cleanup of partial startup, and readiness predicates that treat already-satisfied conditions as success. Measure timeout accuracy and cleanup after cancellation, not only successful action latency.
- **Snapshot convenience is now parity; efficient discovery is the remaining opening.** Playwright MCP supports subtree and depth-limited snapshots, text search, output files, and automatically refreshed snapshots after actions ([snapshot docs](https://playwright.dev/mcp/snapshots)). It documents that refs are snapshot-scoped and must be refreshed when the page changes. Scout should make its existing bounded, scoped, searchable observations easier to compose: return a compact locator/evidence record, preserve its target and frame identity, then allow a deterministic follow-up action while detecting stale references. This is a stronger product workflow than simply offering another snapshot format.
- **Security claims require end-to-end enforcement.** Stagehand has an open report alleging that its domain policy does not cover service-worker requests and WebSockets ([#2945](https://github.com/browserbase/stagehand/issues/2945)). Treat this as an adversarial test idea, not a confirmed general weakness. For Scout, any domain allowlist or policy feature should cover page, frame, worker, redirect, and WebSocket paths, with a traceable denial result. Avoid a broad security promise until those paths have been independently exercised.
- **Feature breadth creates its own complexity cost.** Agent-browser's current command references include session restore, tab pinning, diagnostics, plugins, provider integrations, WebMCP, and an expanding command surface ([command reference](https://github.com/vercel-labs/agent-browser/blob/main/skill-data/core/references/commands.md), [session guide](https://github.com/vercel-labs/agent-browser/blob/main/skill-data/core/references/session-management.md)). Playwright MCP likewise exposes many optional capability groups. Scout can be easier to adopt by making a small number of typed Go operations compose cleanly, with the CLI and MCP exposing those same operations. Keep specialized tools behind capability groups where their setup or output cost is high.
- **A credible benchmark needs to isolate the browser layer.** BrowserGym provides a common API across web-agent benchmarks such as MiniWoB++ and WebArena ([BrowserGym overview](https://huggingface.co/docs/openenv/environments/browsergym)). Those evaluate an agent plus its browser interactions, so they should complement rather than replace Scout's deterministic fixtures. Keep the model, prompts, task set, and adjudication fixed when comparing browser tools; separately publish the browser-layer measures Scout controls: false-success rate, target drift, deadline compliance, recovery after browser restart, result bytes, and resource use. Include successful and failed outcomes, and retain repeat counts and environment versions.

**Strategic update:** reliability, sessions, snapshots, and broad tool coverage are competitive table stakes. The best chance to be better is to make Scout the most inspectable embedded browser runtime for Go: caller-owned sessions, stable target identity, bounded and searchable observations, verified action outcomes, and cancellation/recovery behavior that is consistent across Go, CLI, and MCP. The moat is a documented contract plus reproducible cross-entry-point evidence. The issues above motivate cases to test; they do not establish that Scout already wins them.

### New research signals (5 November 2026)

Recent public issues reinforce that the main product gap is predictable execution under real session conditions, rather than missing action primitives:

- **Session ownership and isolation:** a Playwright MCP report describes cross-client page/context bleed when concurrent clients share a browser context ([microsoft/playwright-mcp #1631](https://github.com/microsoft/playwright-mcp/issues/1631)). An agent-browser CDP report describes commands silently targeting a different tab than intended ([vercel-labs/agent-browser #1867](https://github.com/vercel-labs/agent-browser/issues/1867)); newer reports also cite background-tab close invalidating active-tab refs ([#2407](https://github.com/vercel-labs/agent-browser/issues/2407)). Scout can compete by making session ownership, active-target identity, and post-action URL/target verification explicit, then proving them under concurrent and tab-switching workloads.
- **Bounded observation under stress:** a Playwright MCP report describes accessibility snapshot serialization crashing on a moderately complex Blazor page due to an oversized string ([microsoft/playwright-mcp #1474](https://github.com/microsoft/playwright-mcp/issues/1474)). Scout already has a global serialized MCP response ceiling, capped/paged extraction, and disk-backed snapshot reads. Its opportunity is to verify that the cap applies before expensive intermediate allocations and across every result path, then publish peak memory and recovery behavior as well as response size.
- **State-aware semantics:** recent Stagehand issues include already-idle network waits timing out ([#3370](https://github.com/browserbase/stagehand/issues/3370)), missing cross-site iframes loaded after an action ([#3321](https://github.com/browserbase/stagehand/issues/3321)), and stale frame ownership after nested pages close ([#3240](https://github.com/browserbase/stagehand/issues/3240)). Recent Playwright MCP releases also list fixes for modal/inert targeting and hidden text in accessibility output. This is a reminder that accessible snapshots and waits need state-aware semantics and ongoing compatibility coverage.
- **Operational fit:** issue trackers also show launch, daemon, Windows, and remote-CDP failures (for example agent-browser [#2369](https://github.com/vercel-labs/agent-browser/issues/2369) and Stagehand [#3359](https://github.com/browserbase/stagehand/issues/3359)). Scout should make local and remote CDP setup diagnosable, with actionable health output and cleanup guarantees, but should not build a hosted browser fleet to chase a different product category.
- **Value-to-action provenance:** a recent Stagehand request asks for structured extraction to return both a value and the DOM element it came from ([#3406](https://github.com/browserbase/stagehand/issues/3406)). This is an individual open request, not evidence of broad demand. It suggests a focused experiment: return bounded extracted records with target ID and stable element references, then allow deterministic code to select and act on a matching record without asking a model to rediscover the element. Measure stale-reference rate and end-to-end tool calls against a separate extract-then-observe flow before investing.
- **Independent task benchmark:** the WebdriverIO Browser Agent Benchmark keeps model, harness, and prompt fixed while swapping browser tools, and publishes prompts, judgments, pinned versions, success, cost, tokens, time, and tool calls ([methodology](https://benchmark.webdriver.io/)). Its live-site limits and judge disagreement mean results are noisy, but it offers a useful external comparison alongside Scout's deterministic failure fixtures. Add Scout only through a documented adapter and report its orchestration overhead rather than treating raw tool totals as equivalent.

These are individual public reports, not estimates of incidence. The opportunity hypothesis is that teams will prefer an engine that makes target identity, action outcomes, resource limits, and recovery behavior inspectable. Existing Scout work points in that direction, but does not establish superiority until the same failure-injection fixtures run against Scout and competitors with pinned versions and reported resource measurements.

### Research refresh: lifecycle and operation contracts (5 November 2026)

The newest evidence makes session lifetime a clearer product opportunity than adding more browser primitives:

- **Competitors already offer idle cleanup.** Playwright MCP now documents an `--idle-timeout` that closes owned browsers after a period without completed tool calls; its current docs explicitly distinguish locally owned browsers from CDP or extension connections, where timeout only disconnects. Agent-browser's daemon defaults to idle shutdown after one hour and lets operators configure the period, while preserving headed and user-attached browsers. Playwright MCP issue [#1795](https://github.com/microsoft/playwright-mcp/issues/1795) described a real deployment where HTTP/SSE keepalives prevented the prior idle timer from firing and abandoned isolated sessions accumulated hundreds of Chrome processes. The merged [Playwright PR #43527](https://github.com/microsoft/playwright/pull/43527) gives each isolated client its own timer, closes that client's context when idle, and closes the shared browser when no client contexts remain. This is evidence of an operational need and an upstream fix, not a current Playwright defect.
- **Scout's current lifecycle is explicit close or process exit.** The MCP server owns a session map and closes its sessions when the stdio server exits; during ordinary inactivity it has no MCP idle timeout or session/browser capacity setting. Named sessions otherwise live for the server process and can be explicitly closed; reset/reconfiguration can also relaunch or replace browser state. The Go API gives embedding code `Session.Close()`. This is a gap for hosts that keep an MCP process alive across inactive work, especially when named sessions accumulate.
- **A differentiated implementation should be ownership-aware.** Add opt-in per-session idle expiration and a configurable session cap. Start the idle clock from completed MCP tool activity (not transport pings), report `last_activity`, `idle_deadline`, and the next action (`will_close` or `will_disconnect`) in session status, and never close a browser Scout does not own. For launched sessions, close the browser and state clearly whether cookies are lost; for remote CDP, disconnect only. Default behavior should preserve current sessions so existing users do not unexpectedly lose login state. This recommendation is an inference from competitor docs and the issue report.
- **Target continuity remains a companion opportunity.** Agent-browser issue [#2407](https://github.com/vercel-labs/agent-browser/issues/2407) reports that closing an unrelated background tab clears active-tab refs and frame scope; its reproduction is specific and the report remained open when checked. Scout's own benchmark already exercises target continuity and background-tab actions, but should add the exact “close unrelated tab, reuse existing frame evidence” workflow before claiming a broader advantage.
- **Wait semantics expose the cost of hidden selector fallbacks.** Agent-browser issue [#2405](https://github.com/vercel-labs/agent-browser/issues/2405), reported against 0.41.2, says snapshot refs and XPath passed to `wait` time out because its handler treats evaluation errors as false; malformed selectors reportedly consume the full 25-second timeout. Open PR [#2406](https://github.com/vercel-labs/agent-browser/pull/2406) now proposes ref waits, XPath support, and fast invalid-selector errors. Scout validates CSS syntax before polling and returns a typed invalid-selector error in its Go API and MCP `wait_for`; however, its wait contract is CSS-oriented (with Scout's text-selector fallback), not a general ref/XPath locator contract. The durable opportunity is a coherent typed locator contract across observe, wait, and action, with compatibility costs measured before adoption. Treat both PRs as proposed fixes until released.

**Implementation update:** Scout has opt-in MCP per-session expiration through `SCOUT_SESSION_IDLE_TIMEOUT`, disabled by default, and a configurable `SCOUT_MAX_SESSIONS` cap, also disabled by default. Both settings now reject malformed, zero, or negative configured values during startup, so a typo cannot silently disable the requested lifecycle bound. The cap counts active sessions, concurrent startup reservations, and pending or uncertain closes; same-session lazy startup calls join the in-progress startup. It applies across the stdio process and independently per stateful HTTP client, matching their session ownership scopes. At capacity, creation returns `SCOUT_SESSION_LIMIT` with a recovery hint; no active session is evicted. A failed close remains counted because the browser's final state is uncertain. Existing lifecycle fixtures cover owned and remote expiry, sibling fairness, a long in-flight call, and cleanup behavior. A matched 5-run comparison found Scout preserved a 1.8-second `browser_wait_for` under a 1-second idle threshold in 5/5 trials, while Playwright MCP 0.0.84 closed its context during the call in 5/5 fresh-process trials; at a 5-second threshold Playwright passed 5/5. This is a version-specific reproduction of one reported issue, not a general reliability ranking. Next, rerun against later releases and compare cleanup latency, browser process counts, and memory under concurrent creation at the cap. This is a smaller and more defensible wedge than matching the larger competitors' ever-growing action catalogs.

## Vision

Scout helps Go services and agent hosts make an inspectable outcome decision after browser work is interrupted. It binds a task to its owner, browser context, target, policy, deadline, and verification evidence, then preserves uncertainty until the host checks authoritative application state.

The product is an execution layer embedded in the caller's system, not a hosted agent. Local execution and model-optional deterministic actions are useful constraints, but competitors can offer them too. Scout's lead hypothesis is that a Go host can carry one outcome contract from dispatch through process restart and reconciliation across its supported interfaces.

## Who Scout is for

- **Go teams** embedding browser automation in a service, command, or internal tool.
- **Agent builders** who want browser capabilities through MCP without adding another runtime to their stack.
- **Operators and developers** who need an automation to explain its result and recover from failures.

Their common job is to complete browser work inside an existing application and determine whether it succeeded, failed, or remains unknown when execution is interrupted.

## Product promise

1. **Truthful task outcomes.** A task distinguishes verified completion, rejection, and uncertainty; a browser response alone never stands in for business truth.
2. **Host-owned resolution.** Stable task identity and a durable cursor let a Go host inspect authoritative application state before it records a resolution or starts follow-up work.
3. **Bound identity and policy.** Owner, browser generation, target, origin policy, and deadline stay attached to the operation and are checked before continuing.
4. **Portable execution contract.** Go API, CLI, and MCP expose the same outcome and recovery meaning, even though each transport has its own lifecycle.
5. **Useful evidence with limits.** Receipts distinguish runtime observations from host attestations, redact sensitive page data by default, and make missing evidence explicit.
6. **Low-friction Go integration.** Core deterministic execution needs no model provider; the adoption study must establish whether Scout reduces actual host code and operator effort.

## Where Scout can win

### MCP protocol direction

Scout uses stateful Streamable HTTP by default and has an opt-in stateless mode behind `SCOUT_MCP_HTTP_STATELESS=true`. MCP 2026-07-28 uses per-request metadata; `server/discover` is optional, not a required first call. The mode requires configured principal authentication and an opaque, caller-carried Scout session handle in `_meta`, so removing the transport session header does not erase client isolation. Chrome-backed integrations cover principal and session isolation, task/artifact ownership, idle cleanup, cancellation, and graceful single-process restart: stale handles fail while fresh handles work after restart. Independent TypeScript and Python clients also pass a session-bound navigate/read flow, cancel an in-flight wait, and successfully read again with the same handle. Multi-replica load balancing and additional client SDK compatibility remain open; retain stateful HTTP as the default until those deployment cases are covered. Treat a dropped response as ambiguous until cancellation or reconciliation establishes what happened. See the [competitive opportunities research](competitive-opportunities.md#mcp-stateless-transport-compatibility-6-november-2026).

The finalized sessionless SEP sharpens the design requirement: a model or client must carry application handles explicitly, and the server must authorize them against the authenticated principal; transport session removal does not remove application state. The SEP also leaves the relationship between a handle returned by one tool and an input accepted by another implicit in names and descriptions. Make Scout's handle lifecycle easy for clients to preserve and rediscover, keep browser and task handles separate, and never treat either as replay authorization. The current `_meta` prototype has not been verified against target clients. A normal `session_id` argument requires a field in every browser-scoped tool schema: Scout's pinned MCP library closes struct-derived schemas and validates arguments before handler execution, so a middleware-only alias would fail. See the [10 November stateless MCP research](competitive-opportunities.md#competitive-refresh-stateless-mcp-makes-application-state-explicit-10-november-2026).

Competitors are converging on the same surface area: CLI and MCP access, persistent sessions, screenshots, accessibility or DOM snapshots, and agent-oriented commands. Playwright MCP is adding modular capability sets and controls for context size. Vercel’s agent-browser combines a Rust CLI, daemon, sessions, skills, and provider integrations. Stagehand focuses on model-assisted `act`, `extract`, and `observe`, with hosted Browserbase services.

Scout's product hypothesis is an **embedded Go outcome contract**: durable operation identity, explicit uncertainty, and evidence-backed host resolution across worker and transport boundaries. Local execution, model optionality, replay, MCP coverage, and broad controls are supporting capabilities or parity requirements. The hypothesis earns a market position only if clean-checkout studies show a meaningful integration or recovery advantage and target operators report recent costly incidents.


Recent lifecycle work extends this position from results to operation: Go session creation now accepts a startup context, and MCP clone, capture, assertion, trace, profile, cookie, viewport, tab, frame, batch, replay, and common mutation flows pass request deadlines through their browser work. Context-aware operations also bound session-lock queueing, so a canceled caller does not wait indefinitely behind another action. These changes are verified by focused transport/queue checks; live cancellation during Chrome work and cleanup after real browser disconnects still need runtime benchmark coverage before Scout can make a stronger reliability claim. `status` now also reports the active tab name and CDP target ID with its current URL, so operators can correlate a health snapshot with the page subsequent actions will use.

### Recommended differentiation bets

1. **Verifiable browser actions.** Standardize action, target, outcome, evidence, and recovery fields across all mutations, including submit and tab/frame operations. Let callers assert response status, URL, visible state, value, or exact count. Expose the same schema through Go and MCP.
2. **Context with a hard budget.** Every result should carry size/total/truncated metadata; large content should be written to an artifact and made searchable or sliceable through Scout. Apply bounds after serialization as well as before it, and test binary/image payloads separately.
3. **Scope as a safety and cost contract.** Carry scope through observation, lookup, action, and extraction. Report the effective scope and whether each requested target was resolved inside it. Add fixtures for nested frames, open shadow roots, portals, empty scopes, and selectors that match outside scope.
4. **Replay that earns trust.** Treat playbooks as versioned executable artifacts with assertions, digests, failure evidence, resumability, and a benchmark for replay success after controlled UI changes. Keep model-based repair as an optional caller decision.
5. **Go adoption wedge.** Position Scout clearly for Go developers: a single binary MCP option, embeddable session API, examples that run in CI, clear browser ownership, and parity tests so CLI/MCP/library behavior does not drift.

### What not to chase yet

Do not prioritize hosted browser fleets, autonomous agent loops, huge tool catalogs, or cross-browser claims before reliability is measured. Competitors already have stronger mindshare and larger surfaces there. Avoid advertising absolute reliability or security based on isolated GitHub reports; publish benchmark setup and results instead.

## Product principles

- Prefer deterministic browser operations; use model reasoning at the points where a task needs judgment.
- Verify state after actions that mutate a page, and return concise evidence with the result.
- Put explicit bounds on text, image, and network output. Indicate when data is truncated or saved as an artifact.
- Make session ownership, isolation, reset, and persistence behavior clear to callers.
- Keep security controls understandable: trusted browser endpoints, optional site restrictions, and careful handling of authentication data.
- Expose advanced capabilities progressively so a new user can accomplish a basic task without learning every tool.

## Boundaries

- Scout is not a hosted browser farm or a general-purpose autonomous reasoning service.
- Scout should not compete by maximizing the number of MCP tools.
- Cross-browser support is valuable only after the core execution contract is reliable on supported Chromium browsers.
- “Stealth” is not the product promise. Reliability, observability, and user-controlled automation are.

## Execution sequence

### 1. Make action outcomes dependable

Define a consistent result for navigation, clicks, form filling, and replay: action, target, observed outcome, evidence, and a useful recovery hint on failure. Do not report success solely because a command was sent to CDP or a DOM value was assigned.

The first implementation slice adds action/target/outcome/evidence/recovery fields to page-level results, requested-versus-observed values to typed and filled fields, and atomic text/URL/visibility/value/count postconditions to selector, label, stable-handle, and visible-text clicks, drag-and-drop, generic event dispatch, and navigation. Value checks read back an input or contenteditable value; count checks compare the exact number of selector matches. Navigation reports `navigation_completed` with the actual final URL, including after redirects. Frame switching now reports `frame_selected` or `main_frame_selected` with URL/title evidence read from the selected execution context. Typed, selected, filled, and uploaded-file inputs report `value_verified` or `value_mismatch` after live DOM readback; file selection verifies the filename on the input but explicitly does not claim site-side upload acceptance. Semantic form filling sets success only when the observed value or checked state matches the request and includes a recovery hint on mismatch. Event receipt alone remains `event_observed` and does not claim an application effect; explicit page postconditions report `postcondition_verified` or `postcondition_failed`. Batch steps accept per-step text, URL, visibility, value, or exact-count checks and distinguish action errors, failed expectations, and unverified effects. Form submission reports `response_observed`, `application_accepted`, HTTP status, evidence, and recovery guidance as separate structured fields, and captures matching CDP responses across full-page navigation, including error statuses. A successful HTTP response or navigation is explicitly unverified as application acceptance; callers may use generic `expected_*` predicates to verify page state or explicit `acceptance_*` predicates to assert business acceptance after a response. Direct focus, hover, and scroll checks verify their own narrow browser-state conditions. Replay failures include their phase, current URL/title, a short page text excerpt, and a suggested recovery step. The page excerpt comes from Scout’s existing bounded observation path.

Frame selection now carries an explicit identity into `PageResult` and `Observation` through `frame_id`; their URL/title/text evidence describes the selected frame. Core `Eval`, `Observe`, readiness, content reads, selector waits, clicks, typing, and extraction follow the selected frame. Frame CSS targets are marked in that document and mapped back to the browser DOM before interaction. Opening or switching tabs resets selection to the new page's main frame, preventing an execution context from leaking across CDP targets. This makes frame workflows inspectable without implying every specialized diagnostic or page-wide operation is frame-scoped; those APIs remain a consistency gap.

Action outcome coverage is partial. Double-click and right-click now accept the same optional text, URL, visibility, exact-value, and exact-count postconditions as ordinary clicks through their Go session methods and MCP tools. Without a condition, receipt of `dblclick` or `contextmenu` is reported as `event_observed` with `verified: false`; listener receipt and an uncanceled dispatch do not prove an application effect. MCP `submit_form` now supports an `action_timeout_ms` separate from its response-observation `timeout_ms`; when a submit is uncertain, the supplied expected or acceptance page condition and any already-observed HTTP method, sanitized URL, and status are retained in the recovery record. A local live-MCP fixture has verified late click, type, and submit effects can each be reconciled on the same target. This is a contract fixture, not repeated or cross-browser evidence. Many less common mutation tools still need consistent result fields and optional caller postconditions; file selection now has a structured specialized outcome. More domain-specific predicates such as response status and element attributes may still be useful when workflows demonstrate the need. Continue extending the shared result contract across remaining mutations, then verify the MCP schemas match Go behavior.

**Done when:** common mutating actions verify the resulting page state; failures distinguish target-not-found, timeout, navigation, and session failures; Go and MCP callers receive the same meaningful outcome.

### 2. Make budgets and artifacts consistent

Apply output limits across all MCP results, not just observations and screenshots. Return explicit truncation metadata and an artifact path or reference for large results. Keep secrets out of routine diagnostics and summaries.

**Done when:** every potentially large output has a documented limit, reports whether it was truncated, and has a usable path for the full result where appropriate.

The output-budget implementation covers MCP `markdown`, `readable_text`, and `accessibility_tree` with length, maximum, and truncation metadata; table extraction now caps rows, columns, and cell text. `discover_form` and visual element lists report capped counts, network request and failure details have fixed response limits, and console messages are length-limited and retained in a bounded browser buffer. `compare_tabs` now collects at most 40 heading/price/link entries per page, clips compared values at 256 characters, and reports source totals plus truncation. MCP `extract` is capped at 4,000 characters; tab and cookie listings are capped at 50 and 100 entries. Screenshot, annotated screenshot, and hybrid image responses are capped at 80 KB; annotated/hybrid default width is 1024 px. PDFs larger than 80 KB require disk output. MCP `extract_all` returns pages of up to 8 items, clips each item at 4,000 Unicode characters, and reports original lengths and per-item truncation; `has_more` and `next_offset` provide an explicit continuation cursor, while `items_truncated` distinguishes clipped item text from additional matches and legacy `truncated` remains true for either. The Go `ExtractAll` API retains full item text, while `ExtractAllPage` provides bounded pages. `scroll_and_collect` also has item caps, and `auto_extract` and `scroll_and_collect` expose offset/limit pagination so clients can retrieve additional results. Network request retrieval now has oldest-to-newest offset pagination, a three-record page ceiling, and total/truncation metadata so large captured bodies can be recovered in successive MCP calls. The live MCP stress smoke verifies `extract_all` returns eight 4,000-character items with accurate original Unicode lengths and truncation flags under the 256 KB response ceiling; it also retrieves twelve ~27.6 KB network response bodies in four pages, with the largest serialized page at 169,814 bytes. Before paging support, the network call itself had exceeded the ceiling at 678,430 bytes. Observation and DOM-diff outputs now report total counts and truncation; text, URLs, titles, interactive fields, mutation arrays, framework/app state, pattern fields, and network failure details are bounded before serialization. Framework/app state has a 64 KB limit, batch execution accepts at most 100 actions, and a global middleware ceiling rejects any serialized MCP `tools/call` response above 256 KB. This guard also bounds oversized JSON-RPC error responses from tool calls, preserving the error code and replacing oversized detail with a machine-readable `SCOUT_OUTPUT_LIMIT` envelope that reports omission/truncation, size when available, the hard limit, and a recovery hint. Before exact serialization, middleware now uses a conservative lower bound for ordinary JSON strings, maps, slices, and unambiguous exported struct fields; when that bound alone exceeds 256 KB it returns the envelope without building an encoded copy. Custom marshalers and ambiguous structures retain the exact-size path, and the MCP library still performs final JSON-RPC encoding. Disk-backed screenshot/PDF responses, traces, and encoded recordings now include a shared artifact reference with path, kind, MIME type, byte size, and SHA-256 for single files (directory-based frame sequences omit size/hash). MCP now also has `save_page_snapshot` for Markdown, readable text, or accessibility-tree artifacts; `read_page_snapshot` returns bounded character ranges; `search_page_snapshot` returns literal case-insensitive matches with offsets; and `delete_page_snapshot` removes the artifact. Snapshot files use mode 0600, are created exclusively so an explicit output path cannot silently overwrite an existing file, and are removed if writing fails. Reads are restricted to artifacts registered by the current server process, and a digest check rejects changed files. The live smoke saved 360,107 characters, read two 20,000-character ranges, found a case-insensitive match, rejected an unregistered path, and deleted the file. `ContentResult` now includes total length alongside returned length and truncation. Markdown and readable-text snapshots now count Unicode characters while retaining only the requested prefix in a bounded array. Go response clipping uses UTF-8 byte offsets rather than allocating a full rune slice, avoiding a second full-size character array during response construction. Remaining work is continued per-tool review as new tools are added, and making artifact workflows consistent for every capped result.

### 3. Make sessions operable and safe

Document and harden session lifecycle, concurrency, reset, remote CDP attachment, and profile behavior. Add opt-in origin restrictions where they fit the API, with explicit semantics for redirects and subdomains.

**Progress:** `SessionConfig.AllowedOrigins` and `browse.WithAllowedOrigins` restrict top-level navigation, redirects, and HTTP(S) requests surfaced through the page target's CDP Fetch interceptor to exact scheme/host/port origins. This includes intercepted subresources, `fetch`/XHR, and downloads. Default ports are normalized (`https://host` and `https://host:443` match); paths are ignored; subdomains and non-default ports need separate entries. Malformed allowlist entries return a validation error rather than risking a parser panic. The policy is preserved by session reset. Chrome-tagged integration cases verify a cross-origin redirect and `fetch` are blocked before the disallowed server receives them. A positive-control service worker claims the page and makes a same-origin `/sw-ran` request before its off-origin fetch; the control arrives and the disallowed server also receives the worker fetch. A second case confirms that a cross-origin WebSocket handshake reaches its server, while a configured WebSocket origin is reachable when allowlisted. An attempted `Network.setBlockedURLs` layer did not block either path in the installed Chrome and was removed. `SessionConfig.ProxyServer` carries an HTTP(S)/SOCKS5 proxy through initial launch and reset; Scout now disables Chromium's implicit loopback proxy bypass when a proxy is configured, so localhost requests also pass through that proxy. The repeatable focused runner passed once each for `127.0.0.1`, `localhost`, and `::1`, plus an HTTPS `CONNECT` to IPv4 loopback: every request reached the deny proxy, which returned 403, and every origin recorded zero HTTP requests ([runner](../examples/benchmark/loopback_proxy), capture (local audit artifact)). The HTTPS case correctly surfaced `ERR_TUNNEL_CONNECTION_FAILED`; the runner uses a minimal HTTP proxy, not the mitmproxy addon. Combining `ProxyServer` with `RemoteCDP` now fails at launch because Scout cannot configure an already-running browser; remote browser hosts must enforce egress independently. With the default private-IP restriction enabled, unresolved hostnames fail closed because Chrome has a separate resolver; this does not prevent DNS rebinding between validation and connection. The page-level allowlist is not a complete egress boundary.

**Proxy privacy update:** the mitmproxy reference policy now formats cleartext denial messages from the normalized scheme, hostname, and explicit port instead of the raw URL authority. Embedded URL credentials therefore do not enter the proxy log or its 403 response body. The README records this behavior; it still needs a focused assertion for credential-bearing denied URLs and does not address credentials logged by other proxy layers.

**Done when:** users can predict which browser and page a tool will operate on, restore or reset state, and constrain navigation for unattended workflows.

### 4. Turn successful work into maintained playbooks

Improve recording and replay with step-level assertions, evidence-backed failure context, and a deliberate handoff to the agent when a step needs a new decision. Keep playbooks inspectable JSON and callable from Go and MCP.

**Progress:** replay reports the first failed step with phase, page evidence, and a recovery hint. Recorded actions can be given explicit URL/title/selector/text assertions; replay enforces each provided assertion. `ResumePlaybook` and MCP `resume_playbook` continue after the last completed action and retain prior extracted values. Replay results carry a SHA-256 playbook identity, and resume rejects changed workflows or inconsistent progress. Each failure result also carries a one-use session-bound token tied to the full result, so callers cannot alter progress or safety fields to skip or repeat actions; ambiguous mutation outcomes are marked unsafe and cannot be resumed automatically. Receipts now include the starting-URL navigation as step 0, with declared actions numbered from 1, including failed and retried startup navigation. Browser integration covers repair/resume and failed text assertions. Automatic repair remains intentionally outside the deterministic replay layer.

**Done when:** a recorded representative workflow replays without model calls, identifies the first failed step with page evidence, and resumes after a human or agent repairs the flow.

### 5. Improve adoption in Go projects

Provide a small set of end-to-end examples for library use, CI verification, and MCP setup. Show how to launch or attach to a browser, manage session state, set timeouts, and collect useful failure evidence.

**Done when:** a Go developer can follow tested examples for a local CI task, remote browser attachment, and profile restoration, plus clear instructions for MCP setup, without needing to study the full API.

**Progress:** `examples/ci` now records a click against a local deterministic fixture, attaches an explicit text expectation, saves and reloads the playbook, and replays it without a model call. The default run uses a temporary file; `-playbook PATH` retains the JSON artifact. `SavePlaybook` writes beside the destination and atomically replaces it with mode `0600`, including when an existing file has broader permissions; recordings can contain entered values. `examples/remote_cdp` attaches using environment configuration and disconnects without owning the Chrome process. `examples/profile` saves state, closes its browser, restores it in a fresh session, and verifies the cookie and localStorage against a local fixture. The integration workflow runs the CI and profile examples after the browser suite. README lists runnable scrape, login, CI/playbook, remote, profile, and worker-pool examples, and gives MCP client setup steps for stdio, executable paths, and remote CDP configuration. On 2026-11-05, fresh `go run ./examples/ci`, `go run ./examples/profile`, and `go run ./examples/benchmark` runs succeeded; CI verified and replayed one action, profile restoration verified cookie and localStorage in a fresh session, and the versioned benchmark passed 29/29 scenarios with zero Scout false successes. ## Competitive research addendum: identity, recovery, and session lifetime

**Research checked 5 November 2026.** These GitHub reports are evidence that developers encounter the scenarios, not evidence of frequency across the market.

### New opportunity: recoverable, named browser sessions

Playwright MCP issue [#40585](https://github.com/microsoft/playwright/issues/40585) proposed routing MCP calls by `sessionId` and adding list/close lifecycle tools to support isolation and concurrent work. The maintainer closed it with guidance to run multiple servers or use Playwright CLI. A separate [named-session request #1530](https://github.com/microsoft/playwright-mcp/issues/1530) surfaced both role isolation and handoff of authenticated state. Its discussion distinguishes save/restore for CI from controlling an already-open authenticated profile for desktop agents. These reports suggest that “one server, one implicit browser” creates friction for teams that need parallel identities or agent handoff.

**Scout bet:** make session ownership explicit before adding agent orchestration: stable session IDs, a small `list/status/close` lifecycle, clear attach-vs-own semantics, and a documented way to snapshot/restore state. Add parallel isolation only if separate browser contexts can be guaranteed; otherwise return an explicit conflict instead of implying safe sharing. Treat “which identity is this?” as operator metadata, not automatic cookie-based identity inference.

### New opportunity: explain and recover after disconnects

[Playwright issue #41617](https://github.com/microsoft/playwright/issues/41617) was corrected by its reporter: the session recovered on a second call, but the first disconnect error often led an agent to abandon its authenticated state. The practical opportunity is transparent session health and a safe retry/reconnect affordance that preserves or clearly invalidates page state. Never silently replay a mutating action after reconnect unless the action is idempotent or the caller supplied a postcondition.

**Scout bet:** classify disconnects as recoverable vs terminal, include session/page continuity in the error, expose a health check, and permit a bounded retry only for read-only operations. Mutations should return “outcome unknown” when the transport drops after dispatch, then let the caller inspect state before retrying.

### New opportunity: lifecycle defaults that prevent leaks

[agent-browser issue #1536](https://github.com/vercel-labs/agent-browser/issues/1536) reported daemon and Chrome processes surviving unclean client exits; discussion distinguishes daemon-held sessions that an idle timeout can reclaim from orphaned browser process trees that need a separate cleanup strategy. The report was closed, and the issue cites the existing timeout as working but opt-in. [agent-browser issue #1660](https://github.com/vercel-labs/agent-browser/issues/1660) also describes one stuck `Runtime.evaluate` blocking a per-session queue and making unrelated calls wait behind it.

**Scout bet:** specify session lifetime as part of the API: who owns the browser, what happens on MCP disconnect, whether idle expiry is configurable, and how wedged commands affect the queue. Keep safety conservative: do not kill an externally owned CDP browser; do expose stale-session diagnostics and cleanup only for processes Scout launched. Measure orphan processes and time-to-recovery in integration runs.

### Research-driven priority update

These reports reinforce the existing lifecycle bet, and sharpen it into three independently testable contracts:

1. **Identity and isolation:** two named sessions can hold different authenticated state without cross-talk; same-session concurrency has documented serialization.
2. **Outcome after transport loss:** read-only calls can recover safely; mutating calls distinguish confirmed completion from unknown outcome and are never blindly replayed.
3. **Resource ownership:** Scout cleans up what it owns, preserves what it attaches to, and gives operators a clear idle/health/close path.

Before investing in session-manager breadth, add benchmark fixtures for two identities, disconnect-before/after-action, and idle-client exit. Publish the ownership matrix for launched, attached, and restored sessions. Those results will say whether session isolation or recovery should lead the roadmap.

### Recommended product promise

**“Browser operations you can trust and replay from Go.”** A successful mutation should identify its target, report whether it was attempted, state what was observed afterward, include concise evidence, and say what to do when the result is unknown. The same operation should mean the same thing through Go, CLI, and MCP. A recorded workflow should replay without an inference provider and stop at the first unverified step with enough evidence to recover.

This promise should be earned with published results rather than broad “most reliable” claims. Keep performance and completion claims scoped to pinned tools, browsers, fixtures, and adapters.

### Where to be better than the competition

1. **Make false success hard.** Define one outcome schema for navigation, click, type, submit, and other mutations. Separate “command accepted,” “response observed,” and “application state verified.” On timeout or disconnect after dispatch, report `outcome_unknown`; never imply failure or success without evidence, and never retry a non-idempotent mutation automatically.
2. **Make recovery part of the result.** Return the failed playbook step, captured page evidence, and a concrete next inspection or repair action. Resume from that step only after the caller has repaired state. This is a practical middle ground between brittle scripts and opaque autonomous healing.
3. **Make scope and budgets enforceable.** Every relevant action and observation should respect the requested root, and every MCP result should respect the documented byte ceiling after serialization. When content is too large, return a registered artifact handle and bounded read/search operations with explicit offsets and truncation metadata.
4. **Make sessions predictable for embedded teams.** Preserve the current named-session isolation and ownership rules; add health and cancellation behavior only where it is consistent across Go/MCP transports. Document that local launched browsers are owned and cleaned up while attached remote browsers are detached and preserved. Do not promise parallel access to one page when operations are serialized.
5. **Make first use smaller than the alternatives.** Keep the same engine usable as a Go dependency, command, and MCP server. Offer copyable examples for local CI, remote CDP, profile restoration, and replay. Measure install-to-first-verified-action, not the number of tools.

### Further research: advantage beyond feature parity

The current issue scan (5 November 2026) points to a sharper competitive position: Scout should be the browser automation layer that tells an operator exactly what happened, contains the run within declared limits, and leaves enough evidence to recover. These are recurring pain categories in public reports, not claims about how often competitors fail:

- **Wrong-target and false-success risk:** [agent-browser #1867](https://github.com/vercel-labs/agent-browser/issues/1867) describes silent tab drift under CDP attachment; [#2146](https://github.com/vercel-labs/agent-browser/issues/2146) reports a background-tab click returning “Done” without the page handler running. Scout can differentiate with target identity in action evidence and a postcondition that checks the intended page, not just command dispatch.
- **Context and element coverage:** [agent-browser #2246](https://github.com/vercel-labs/agent-browser/issues/2246) reports missed custom clickables inside shadow roots. Playwright’s current approach combines compact accessibility snapshots and refs with screenshots for visual-only cases ([snapshot docs](https://playwright.dev/mcp/snapshots), [screenshot docs](https://playwright.dev/mcp/tools/screenshots)). Scout should present this as a mixed evidence strategy and test nested frames, shadow roots, canvas, and visual fallback explicitly, rather than claim semantic snapshots alone solve targeting.
- **Security boundaries:** [Stagehand #2945](https://github.com/browserbase/stagehand/issues/2945) reports domain policy bypass through service-worker fetches and WebSockets. Scout applies its origin policy to navigation, redirects, and HTTP(S) requests surfaced through the page target's Fetch interception. Service-worker-owned traffic and WebSocket handshakes bypass that check. `SessionConfig.ProxyServer` lets agent users route a launched browser through a policy-enforcing proxy, but Scout does not generate proxy rules from `AllowedOrigins`; do not market the page-level allowlist as complete egress enforcement.
- **Session operations:** [Playwright MCP #1795](https://github.com/microsoft/playwright-mcp/issues/1795) documented leaked browser processes when an idle client kept its connection open; the report was later closed as fixed. Stagehand reports also cover stale frame references after tab changes ([#3240](https://github.com/browserbase/stagehand/issues/3240)) and commands whose transport deadline is shorter than the requested wait ([#3369](https://github.com/browserbase/stagehand/issues/3369)). Scout can make ownership, health, deadlines, and cancellation observable in one session lifecycle contract.
- **Proving real quality:** WABER argues for measuring reliability and efficiency alongside task success ([Microsoft Research](https://www.microsoft.com/en-us/research/publication/waber-evaluating-reliability-and-efficiency-of-web-agents-with-existing-benchmarks/?lang=fr-ca)); ST-WebAgentBench adds whether a task was completed within policy ([IBM Research](https://d3ccyth396mz21.cloudfront.net/publications/st-webagentbench-a-benchmark-for-evaluating-safety-and-trustworthiness-in-web-agents)). This aligns with Scout’s outcome, replay, and allowlist foundations: publish false-success rate, safe completion rate, recovery time, and cost/latency rather than a single success percentage.

### Fresh opportunities

1. **Prove bounded failure, not just successful flows.** Public reports describe browser calls that can wedge a session or queue when a target does not respond (agent-browser [#1713](https://github.com/vercel-labs/agent-browser/issues/1713), [#1660](https://github.com/vercel-labs/agent-browser/issues/1660)). 2. **Make policy behavior inspectable at the boundary.** Managed browser products are increasingly packaged with centralized credentials, policy, and session observability (for example, [Microsoft Foundry Browser Automation](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/browser-automation) runs over managed Playwright Workspaces). Scout should expose a small default workflow and let callers opt into breadth. Measure generated agent/tool schema size, calls to a verified result, and glue code for the same task; do not assume a smaller Go binary automatically means lower agent cost.
4. **Turn uncertainty into a useful handoff.** When transport fails after a click or submit may have dispatched, persist target identity, operation, timestamp/deadline, response evidence available so far, and an inspection hint. The caller can inspect before deciding to retry. This is more valuable to services than an automatic retry that could duplicate a purchase, message, or record update. **Current Scout slice:** typed unknown-outcome errors carry a per-session run ID and one-based unknown-outcome sequence (`step`), a separate session-wide `operation_ordinal`, target, frame, redacted current URL, expected condition, caller deadline, configured timeout, explicit session-health fields, inspect-before-retry hint, and trace ID/step when tracing is enabled. Scout now exposes a shared `ActionRecoveryRecord` API with validation and decoding; the record preserves run ID, operation ordinal, textual evidence, typed outcome, and optional observed HTTP response method, sanitized URL, and status for form submissions where the response was seen before postcondition verification failed. CLI `--recovery-file=PATH` atomically writes schema-version-3 owner-only JSON; legacy schema-version-1 CLI artifacts remain readable. Go callers can create, persist, decode, and reconcile the same record with `Session.ReconcileActionRecoveryRecordContext`; MCP errors carry it for `reconcile_action` when target identity is available. Reconciliation checks the saved postcondition without replaying the mutation. Version-3 records also carry a SHA-256 fingerprint of the active DevTools WebSocket endpoint plus BrowserContext, so portable reconciliation rejects a different or unidentifiable browser/context before checking target presence or page state. The fingerprint is non-reversible and is not a credential. A browser restart changes the DevTools endpoint identity, so this action-level record still requires the original browser; otherwise reconciliation returns a structured identity error with manual-inspection guidance and the outcome stays unknown. Hosts using the durable task-run store can instead preserve the reservation and record a conclusion from authoritative application evidence through a fresh session, without restoring the old page. The two-process delayed-click benchmark checks run/unknown-outcome-sequence identity, health-field retention, deadline/timeout fields, target binding, and permissions. Browser-backed tests prove late click reconciliation on a reconnected same browser, rejection against a different browser even after its separate target is closed, rejection across isolated contexts on one browser endpoint, and late close reconciliation with registry repair. Unit tests reject missing or mismatched browser identities. Action-level record reconciliation remains tied to its original browser/context identity. Durable task-run host reconciliation after browser replacement is now demonstrated by the example, but it depends on application-owned evidence and does not recover the old page. Ephemeral isolated contexts are disposed with their owner and must be reconciled before session closure. Other mutation paths and submit interruptions before a response is observed still cannot report typed response details. Measure recovery time/operator steps across all entry points.

The strongest opportunity is to make Scout the **local execution control plane for Go applications**: a small embeddable engine that composes caller deadlines, target identity, origin/scope policy, output/resource budgets, application-level verification, and a portable recovery record. Let users bring their own browser provider when they need fleet scale. Earn differentiation by showing exactly which policy decision was applied, which target received a mutation, whether it was dispatched, what condition was verified, and what evidence is safe to inspect or persist after interruption. Scout's built-in `AllowedOrigins` interception remains page-scoped and does not cover service-worker requests or WebSocket handshakes. The repository now has an optional mitmproxy reference integration that tests those paths at an external boundary, but Scout does not automatically configure or enforce that proxy policy.

#### Product opportunities worth testing

1. **Policy proof per action.** Attach the effective origin rule, scope, target ID, deadline, and output budget to a bounded action record. Test navigation, redirects, subresources, downloads, service workers, WebSockets, workers, and new tabs. Report enforcement coverage by path instead of a blanket “safe browser” claim.
2. **Recovery handoff as a first-class result.** The CLI saves the shared recovery record with unknown action details, run/unknown-outcome-sequence identity, session-wide operation ordinal, textual evidence, target, timestamp, deadline, session-health snapshot, expected postcondition, inspection guidance, and optional observed form-response evidence in a private file; a fresh process can check the same live target. Go and MCP can now create or consume the same record. Extend typed response evidence to other actions where available and verify matched end-to-end recovery. Test whether an operator can resolve a stalled or disconnected workflow faster than with raw logs or a fresh browser.
3. **Provider-neutral browser ownership.** Keep local Chrome and remote CDP as direct modes, but define an adapter seam for managed browser endpoints and provider session metadata. Validate demand before building integrations; do not create a browser fleet.
4. **Small-by-default agent surface.** Offer a coherent core workflow and opt-in capabilities, with generated tool-schema size and token estimates. This follows Playwright's capability model while differentiating through outcome and budget consistency across the selected tools.
5. **Run-level quality evidence.** Export structured traces that join policy decisions, target changes, action dispatch, verification, and recovery. Make these useful to CI and OpenTelemetry pipelines without requiring Scout-specific dashboards.

### Second-pass competitive research: parity is arriving quickly (5 November 2026)

This pass used current product documentation, release notes, and GitHub reports. It changes two assumptions in earlier notes. **Go is not a unique wedge anymore:** Browserbase maintains an official Stagehand Go SDK with examples for local and hosted browser workflows. **Several issue examples are already addressed in later releases:** agent-browser's changelog describes fixes for hidden/disabled/off-viewport click reporting, stale reference recovery, and target invalidation. Treat open issue reports as fixture ideas and always reproduce them against a pinned current release before using them as comparative evidence.

The competitors are converging on capable end-to-end surfaces. Playwright MCP documents 70+ tools, cross-browser support, element refs scoped to a snapshot, frame-prefixed refs, subtree/depth-limited snapshots, `browser_find`, and file-backed snapshots. Its docs also call out the higher context cost of MCP snapshots and position its CLI as a lower-token option for coding agents. Stagehand's official Go package combines semantic `act`/`observe`/`extract`, model-assisted repeatability, and direct page methods. agent-browser combines CLI and MCP, named sessions, batching, persistent state, broad diagnostics, and focused skill references. The relevant references are the [Playwright MCP introduction](https://playwright.dev/mcp/introduction), [snapshot contract](https://playwright.dev/mcp/snapshots), [Stagehand v4 Go SDK](https://github.com/browserbase/stagehand/tree/main/packages/sdk-go), and [agent-browser release history](https://github.com/vercel-labs/agent-browser/blob/main/CHANGELOG.md).

**Strategic implication:** feature breadth, Go bindings, saved snapshots, browser sessions, and replay are not enough to claim superiority. Scout should make a narrower, measurable promise: a caller can set a deadline, scope, origin policy, and output ceiling; every mutation is tied to a specific browser target; and its result distinguishes dispatch from a verified application condition, with bounded evidence that survives interruption. Competitors may offer parts of this contract, so the comparison must establish whether Scout composes them consistently through one Go library, CLI, and MCP engine.

#### Updated research priorities

1. **Measure parity and difference on equal footing.** For each matched fixture, list the competitor's native mechanism, whether Scout supports the same behavior, and any adapter code. Separate unsupported from not tested. Use pinned versions and preserve traces so issue-driven scenarios do not become stale claims.
2. **Benchmark false success and policy escape.** Include wrong-target/background-tab actions, optimistic UI followed by server rejection, redirect and subresource policy, service-worker and WebSocket egress, disconnect before/after dispatch, and oversized structured output. Report pass/fail/unsupported plus false-positive and unknown-outcome counts.
3. **Benchmark operational cost.** Compare wall time, peak memory, serialized output size, model-visible text, and recovery steps for the same task. Playwright itself now recommends the CLI when lower token cost matters, so Scout should show its concise CLI/MCP response path and artifact retrieval against that baseline.
4. **Validate the Go-specific buyer.** Compare Scout with Stagehand Go and direct `chromedp`/Playwright integration on setup time, deployment dependencies, local-browser ownership, cloud/API requirements, deadline propagation, and application-level verification. Go language support by itself is no longer a defensible claim.
5. **Keep security claims scoped to evidence.** Scout's built-in origin interceptor still does not cover service-worker requests or WebSocket handshakes. The mitmproxy reference integration offers an external enforcement path, but users must configure and align its rules separately. Publish coverage by request path and clearly distinguish browser interception from external egress enforcement.

The best near-term advantage is therefore **portable operational evidence**, not a new agent layer: a small run record that lets a Go application answer which target was used, which policy applied, what was dispatched, what state was observed, why verification passed or failed, and how to recover safely. This should remain a product hypothesis until the benchmark and integration-cost study show a repeatable advantage over Stagehand Go, Playwright MCP/CLI, and agent-browser.

#### Fresh opportunity: explicit browser ownership and configuration precedence (5 November 2026)

Two agent-browser reports sharpened the next differentiator beyond target binding. This suggests Scout should make browser ownership explicit and sticky: resolve configuration once at session creation, expose its effective endpoint and owner, and make changes visible in status. Scout implements useful local process and request-level boundaries. The deeper product gap is shared remote browsers: `SCOUT_REMOTE_CDP` can make multiple authenticated MCP clients operate on one external browser, and the shared bearer token does not distinguish callers or assign target ownership. Define whether Scout supports isolated contexts or owner-bound targets in shared authenticated profiles before claiming multi-tenant readiness. Add “explicit connect survives later calls” and cross-owner target access/cleanup fixtures after that policy is chosen.

### Competitive research refresh: win on attributable execution (5 November 2026)

This refresh compared current Playwright MCP documentation and public GitHub issue trackers for agent-browser and Stagehand. It changes the product question from “which browser verbs are missing?” to “can a team trust what happened, across clients, timeouts, and retries?”

**Parity is moving quickly.** Playwright MCP exposes core navigation and interaction plus optional network, storage, testing, vision, PDF, and devtools capabilities; the docs explicitly say capability selection can reduce schema size, hallucinated calls, and processing cost ([capabilities](https://playwright.dev/mcp/capabilities)). Agent-browser now documents strict tab pinning, tab-gone errors, explicit recovery, and portable browser-state restoration ([session management](https://github.com/vercel-labs/agent-browser/blob/main/skill-data/core/references/session-management.md)). Stagehand offers both deterministic `act`/`observe`/`extract` APIs and agent-oriented behavior, including Go support ([Stagehand](https://stagehand.dev/)). Therefore, broad tool coverage, compact output, Go, snapshots, or basic target IDs are not durable differentiators by themselves.

**Failure reports point to a deeper customer problem: attribution.** Playwright MCP issue [#1631](https://github.com/microsoft/playwright-mcp/issues/1631) reported page events leaking between MCP clients; [#1343](https://github.com/microsoft/playwright-mcp/issues/1343) described work continuing on a background page after a new tab opened. The newer [#42961](https://github.com/microsoft/playwright/issues/42961) surfaces a related ownership requirement in shared-profile deployments. Agent-browser issue [#1713](https://github.com/vercel-labs/agent-browser/issues/1713) reported wedged commands without a per-command deadline, while follow-on [PR #1851](https://github.com/vercel-labs/agent-browser/pull/1851) remains open and undeployed; merged [PR #2396](https://github.com/vercel-labs/agent-browser/pull/2396) now makes session setting changes and relaunches explicit. These are time-stamped reports, not estimates of how often users encounter the failures. They suggest an opportunity to make every result answer: which caller, session, target, frame, action, and deadline produced this evidence, and what is safe to do next?

Trace continuity belongs in that contract too. Playwright issue [#42423](https://github.com/microsoft/playwright/issues/42423) described context tracing silently producing an incomplete archive after a renderer disruption while subsequent calls appeared successful; it was closed as completed by [#42425](https://github.com/microsoft/playwright/pull/42425). This is a fixed upstream regression report, not a current weakness claim. It gives Scout an adversarial acceptance case: after renderer recovery or target replacement, the action record and trace should say which browser target produced evidence, whether context continuity changed, and whether the exported trace validates as a usable artifact. An action receipt without artifact health would leave operators with an incomplete audit trail.

**Recommended position:** Scout is the browser execution runtime that makes agent actions auditable and recoverable across Go, CLI, and MCP. The differentiator should be one versioned action record with stable operation identity; explicit preconditions and postconditions; target/session ownership; deadline and cancellation state; before/after evidence; and a safe reconcile/resume instruction. This is stronger than a collection of isolated recovery features because teams can store the record, correlate it with application telemetry, and build their own retry policy without adopting Scout's agent loop or hosted browser service.

#### Priority bets after the issue scan

1. **Operation identity and portable recovery journal.** The shared versioned recovery record now spans Go, CLI, and MCP. Action receipts carry a session-wide `operation_ordinal`; recovery records retain the run ID and link reconciliations to that operation. Playbook receipts carry a one-based step and attempt. Trace-local action ordinals remain distinct. Keep these identities aligned across every entry point and ensure retries preserve lineage. A recovery record must identify its target and predicate and must never silently replay a mutation.
2. **Matched concurrency contract.** Scout's Go session mutex serializes browser operations; MCP captures the selected session and active target at call start, and callers can require a specific `target_id`. A task's final postcondition now runs under the same session lock as its actions, closing a gap where another call could mutate the page before the final readback. A Chrome-backed integration regression pauses at the durable `final_verification` checkpoint, queues a competing navigation, and confirms the task verifies first; it passed normally and twice under Go's race detector. This is a serialized single-writer contract, not parallel browser execution. Still prove it with simultaneous clients racing target switches, tab close/open, navigation, storage mutation, cancellation while queued, and the MCP tool path. Check stale-target and timeout results against pinned competitors; return explicit conflicts instead of plausible evidence from the wrong page.
3. **Bounded calls with late-effect accounting.** Publish per-stage timeout behavior for queueing, connection, browser command, verification, and cleanup. Report promptly when caller patience expires, then expose whether a dispatched command may still finish and how to reconcile it. Stagehand's cooperative-cancellation work is an implementation signal; cancellation cannot retract a command already delivered to Chrome ([PR #2394](https://github.com/browserbase/stagehand/pull/2394)).
4. **Evidence quality and efficiency in the same scorecard.** Report task success and false-success rate alongside latency percentiles, action count, output bytes/tokens, deadline overshoot, cleanup time, and recovery success. Browser benchmarks increasingly evaluate complex actions and interventions; success-only scores miss execution cost and fragility ([CAP-Bench](https://warriorxu0302.github.io/CAP-Bench/), [controlled-intervention benchmark](https://arxiv.org/abs/2609.35814)).
5. **Safe, explainable ownership and policy.** Show effective browser owner, endpoint source, session namespace, and policy decision in status and action evidence. Explicitly state which traffic is in scope and which browser channels bypass a page-level policy. This makes Scout's embedded Go/server use case credible without promising a complete network sandbox.

#### What to build and prove next

- Finish a single action-evidence schema across Go, CLI, and MCP. Recovery records carry a session-wide `operation_ordinal`; `step` remains an unknown-outcome sequence, while active traces expose a separate trace-local `action_ordinal` and recovery correlation field. Keep these identities distinct and verify they stay aligned across every entry point.
- Add a concurrency matrix with two independent MCP clients and shared-session clients, then compare the same scenarios against pinned versions of Playwright MCP and agent-browser.
- Turn benchmark output into repeated runs with confidence intervals and raw artifacts; record exact versions, browser build, environment, and failure injection. A local Scout-only pass is a contract check, not comparative leadership evidence.
- Ask 5–10 Go/platform teams how they currently handle browser timeouts, duplicate submissions, and audit requirements. Validate whether portable recovery records and operation-level telemetry solve a budgeted problem before expanding hosted execution or adding many more browser tools.

**Decision:** prioritize attributable operation records, multi-client correctness, and repeatable benchmark evidence. Keep tool breadth, autonomous agent loops, and hosted browser fleets as compatibility or integration choices unless customer discovery shows they are blocking adoption. The product promise should remain narrow until matched competitor runs confirm an advantage: Scout reports uncertainty explicitly and provides the evidence needed to recover safely.

### Principal-scoped MCP HTTP policy follow-up (6 November 2026)

Scout's Streamable HTTP server accepts `SCOUT_MCP_HTTP_PRINCIPALS_JSON`, mapping distinct bearer credentials to stable principal IDs, remote CDP endpoints, exact allowed origins, and an explicit private-IP policy. Principal identity is bound when the MCP transport session is created; later requests and `DELETE` must present credentials for the same principal. Browser session registries and configuration are scoped by both principal and MCP session ID, and `configure` cannot widen a principal's server-set private-IP policy. Principals may share one Chrome endpoint when every principal sets `isolate_browser_context: true`, which creates and owns a separate ephemeral CDP BrowserContext for each Scout session.

Isolated BrowserContexts separate tabs, cookies, and storage, but they do not share authenticated profile state; Scout does not yet provide shared login with per-principal target ownership. Remote CDP providers must support Chromium's create/dispose BrowserContext commands. Origin checks do not replace network egress controls on the remote browser host. The policy is loaded at process startup, so token revocation or endpoint changes require a controlled restart.

**Principal-scoped browser context validation (6 November 2026).** The focused `mcp-http-principal-isolation` fixture assigns two authenticated principals to the same remote Chrome endpoint with `isolate_browser_context: true` and sends both navigations concurrently. Five fresh server/browser runs passed 5/5: each verified distinct targets, isolated cookie/localStorage state, origin restrictions, cross-principal MCP session-ID rejection, context recreation after reset, and principal B survival after principal A deletes its HTTP session. Scenario durations were 1.03–1.58 seconds (median 1.06 seconds), excluding one shared CLI build. Raw output is in the five-run report (local audit artifact). This is repeated local Chromium evidence; provider-specific BrowserContext support and larger concurrency remain unverified.

**Shared endpoint policy (6 November 2026).** Duplicate normalized `remote_cdp` URLs are accepted only when both policies enable `isolate_browser_context`; direct aliases with case and trailing-slash differences are normalized. Reverse-proxy aliases and distinct endpoint paths cannot be identified from configuration, so every principal resolving to the same Chrome must enable isolation. Remote-browser provider support varies. Principal contexts are ephemeral, are disposed on close and recreated on reset, and leave the external Chrome process running.

**Operator visibility update (6 November 2026).** Go `SessionStatus`, MCP `status`, and MCP `list_sessions` now expose `browser_context_isolated`, so a host can audit whether a session is configured for an isolated remote context without receiving the provider's context ID. The MCP lifecycle summary also exposes per-client idle deadlines, active-session caps, and concurrent starting/closing counts. **Network evidence coverage update (6 November 2026).** Trace exports now include `network-manifest.json` beside the backward-compatible `network.json` capture array. The manifest reports `capture_mode` (`not_started`, `diagnostics_only`, `full_capture`, `disabled`) separately from coverage, plus the session capture-window scope, whether capture was ever enabled and is enabled at export, URL filtering, retained/pending/dropped request counts, history limit, and known interruptions. Failure-only diagnostic capture is explicitly labeled `diagnostics_only`; it is not confused with no observer or a full request capture. `clear_network_requests` starts a fresh retained-evidence window and drops any in-flight requests from the previous window, counting those as known gaps. `coverage` now shares the live vocabulary (`not_enabled`, `diagnostics_only`, `known_gaps`, `disabled_at_read`, `active_no_known_loss`), while `capture_state_at_export` retains archive-specific states such as `capture_never_enabled`, `capture_disabled_at_export`, and `no_known_loss_at_export`; even `no_known_loss_at_export` does not imply complete browser-wide traffic coverage or include requests outside CDP's subscribed page targets. A known gap, disabled capture, diagnostics-only mode, or never-started observer is machine-readable without treating an empty array as proof that no requests occurred.

**Trace screenshot coverage update (6 November 2026).** Trace ZIPs now include `evidence-manifest.json`, scoped specifically to trace events and their before/after screenshots. Before-captures abandoned before an event is emitted are counted separately as unattached attempts, so they cannot shift status onto a later action. The authors label it a smoke eval, not broad reliability evidence, and the output-byte counts are not tokenizer-specific token usage ([eval method](https://github.com/vercel-labs/agent-browser/blob/main/evals/README.md)). ### Competitive signal recheck: same-session recovery is being addressed upstream (6 November 2026)

Browser Use #6295 describes a concrete handoff gap: its `retry_with_browser_use_agent` tool starts an independent browser session after structured MCP tools have already prepared a page, so recovery loses the existing live context. Open PR #6298 proposes a `same_tab` option that reuses the active session, preserves domain restrictions and keep-alive state, serializes concurrent retries, and prevents idle cleanup or explicit close from terminating the recovery agent. Its author reports 12 GitHub Actions tests including six real-browser cases, while a local integration attempt failed during Chromium startup; therefore treat the proposed fix as promising but not yet merged or fully locally reproduced. Browser Use #6296 is a separate open request for MCP tools themselves to attach to an already active browser session instead of always creating a new tab on first use ([#6295](https://github.com/browser-use/browser-use/issues/6295), [#6298](https://github.com/browser-use/browser-use/pull/6298), [#6296](https://github.com/browser-use/browser-use/issues/6296)).

**Product implication:** the differentiated opportunity is not merely to preserve a tab. A host needs a handoff contract that carries owner, browser generation, target/frame, policy, task/action identity, and outcome evidence, and that blocks mutation until the receiving runner verifies those bindings. A fresh Scout process and an independent Node receiver now consume the HMAC-signed `scout.recovery-handoff/v1` envelope; the Node receiver also checks the target ID and canonical URL reported by agent-browser against the live browser target. This demonstrates a narrow cross-runner target agreement. The agent-browser observation is unauthenticated and exposes no frame identity, so the Node receiver correctly refuses a full-context match and cannot authorize replay. Owner, policy, and browser-generation values still come from the fixture; a production broker must bind generation and policy to the actual context. The next experiment should provide authenticated owner/generation/policy/frame bindings, then have one runner prepare a delayed mutation, lose or yield control, and a second runner resume on the same browser; grade identity continuity, preserved restrictions, duplicate side effects, and explicit business-state reconciliation. Repeat with a replacement browser, since only the same target should be eligible for page-bound reconciliation. See the [receipt and handoff contract](recovery-receipt-contract.md#portability-and-privacy-rules) and the recorded local run (local audit artifact).

**WebMCP matched smoke and Scout bridge (6 November 2026):** agent-browser 0.41.2 and Playwright MCP 0.0.84 both invoked the same injected `complete_task` tool on Chrome 157 and independently verified the same final DOM text. Agent-browser exposed a compact tool summary on page load, provided a targeted schema lookup, and returned JSON metadata marked `untrusted: true`; Playwright surfaced `webmcp_complete_task` dynamically after a page snapshot and wrapped its description/result with explicit untrusted-content text. Both paths passed this one smoke run. Agent-browser's default launch used `WebMCPTesting`, which did not expose `document.modelContext` in this environment; adding Chrome's `--enable-features=WebMCP` flag fixed it. The reproducible harness and raw observations are in [`examples/benchmark/webmcp`](../examples/benchmark/webmcp/README.md). Scout now exposes experimental CDP discovery and invocation through MCP, bound to the catalog target and frame, with bounded JSON Schema validation and required independent postconditions. Metadata and results remain untrusted; invocation errors after dispatch are treated as uncertain outcomes. This closes a parity gap but does not establish better reliability or a moat. Scout's first live bridge smoke on Chrome 157 discovered the tool through MCP, invoked it, verified a declared postcondition, and independently confirmed fixture state through CDP; the exact run is recorded in [`scout-webmcp-live-smoke.json`](../examples/benchmark/webmcp/scout-webmcp-live-smoke.json). Delayed execution, tab/frame drift, hostile metadata, cross-origin frame policy, accessibility fallback, and repeated agent runs remain unverified. Chrome still describes WebMCP as experimental ([Chrome WebMCP docs](https://developer.chrome.com/docs/modern-web-guidance/guides/webmcp/agentic-javascript-tools)).

### Competitive research correction: page-native execution is converging (6 November 2026)

The WebMCP opportunity has moved from emerging feature to parity work. Playwright MCP documents page tools surfaced from the current tab. Agent-browser's 0.36.0 changelog describes experimental WebMCP discovery/invocation, frame-aware selection, detached results, cancellation, and bounded metadata/output. Its current command and trust-boundary docs also specify on-demand schema retrieval, catalog invalidation, untrusted page metadata, and host-controlled permissions. Scout now has an experimental WebMCP adapter. Its remaining validation opportunity is preserving target/policy identity, page-content provenance, declared postconditions, and durable reconciliation when either UI actions or a page-native tool performs work; the adapter itself is parity, not a moat.

Agent-browser draft PR [#2434](https://github.com/vercel-labs/agent-browser/pull/2434) proposes an APC snapshot source using Chrome's internal annotated-page payload, with viewport filtering and fallback to accessibility snapshots. The draft's own limitations include Chrome-version-specific schema and incomplete in-frame results. Treat it as an experimental upstream direction, not a shipped competitive baseline. The next fair test should pin browser and tool versions, run the same read/mutate/delayed/hostile-tool scenarios through current competitor interfaces, and measure outcome truth, target mix-ups, trust-marker propagation, recovery evidence, output, and setup. See the revised [opportunity matrix](../examples/benchmark/OPPORTUNITY_MATRIX.md). Continue validating the Scout bridge against that test and buyer interviews; shipping another tool surface by itself does not advance the product position.
